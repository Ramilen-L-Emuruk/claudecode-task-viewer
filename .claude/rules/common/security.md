# セキュリティガイドライン

## 必須セキュリティチェック

コミット前に確認:
- [ ] ハードコードされたシークレットがない（API キー、パスワード、トークン）
- [ ] 全ユーザー入力がバリデーション済み
- [ ] SQL インジェクション対策（パラメータ化クエリ、ORM/クエリビルダーの適切な使用）
- [ ] XSS 対策（テンプレートエンジンでの適切なエスケープ処理）
- [ ] CSRF 対策の有効化（利用フレームワークのCSRF機構）
- [ ] 認証・認可の検証
- [ ] エラーメッセージが機密データを漏洩しない
- [ ] ログ出力に認証情報（パスワード・トークン等）を含めない

## シークレット管理

- ソースコードにシークレットを絶対にハードコードしない
- 環境変数または設定ファイル（`.env`、`application.yml` 等）を使用
- `.gitignore` にシークレットを含むファイルを追加
- 漏洩した可能性のあるシークレットはローテーション

> 言語・フレームワーク固有のセキュリティ対策（例: Java/Spring の `PreparedStatement`、Spring Security 設定等）は `rules/java/security.md` 等の言語別ルールを参照。

## 公開する前に個人情報が無いことを確かめる

**リポジトリが公開されているなら**、外へ出すものに個人情報が 1 つも入っていないことを、出す前に確かめる。
**出したものは取り消せない** —— 消しても clone・フォーク・検索の控えに残り、履歴から消すには書き換えと force push が要る。

「テストの値だから」「ローカルの話だから」で、それが個人情報だという判断を挟まずに書き込むのが典型（自宅に置いた機器の座標をテストの既定値へそのまま書いて公開した例がある）。

### 対象

**手元の外へ出るものすべて。** ファイルだけではない。

- **push するもの** —— 送るコミットから届くすべてのファイル（テスト・見本・生成物・画像も）、コミットメッセージ、作者とコミッター、タグのメッセージと作成者、ブランチ名とタグ名
- **リリース** —— 上の push そのもの（`release` スキルの手順 6 で必ず通る）
- **PR・Issue・Gist・コメントの本文**、外部のサービスへ送る文章やファイル

**個人情報**とは、持ち主や住んでいる場所に辿り着ける値のこと。実名・勤め先・メールアドレス・住所・自宅の座標、
**端末の名前・LAN の IP・機器の MAC・ネットワークの名前**、端末の中のユーザー名とパス、鍵とトークン。
**そこから計算した値も含む**（自宅からの距離・方位・到達時間、最寄りの施設や地名）。

**例に使う値は架空のものにする。** MAC はローカル管理アドレス（`02:00:00` のように先頭が `02` のもの。製造元が割り振った番号と重ならない）、
IP は文書用の見本アドレス（RFC 5737）、座標はどこの家でもない丸めた値、機器の名前は役割で呼ぶ（「ホストの機械」）。

### 確かめ方

- **機械の検査を置くなら、照合する具体的な値の一覧はリポジトリに入れない**（入れれば一覧ごと公開される）。一覧が無ければ検査は止まる形にする —— 何も照合しないまま「通った」にしないため。**値はユーザーから受け取る**（Claude が会話や資材から類推して埋めると、一覧が「既に漏れたもの」だけになる）
- **push の前に走らせるフックは、clone した端末ごとに入れる必要がある**（フックは git の管理外）。入っていない端末・Web 画面での編集・CI が自分で行う push には届かないので、その経路では手で確かめる。**`--no-verify` で押し通さない**
- **個人情報から計算した値は、形では見分けられない。** 「自宅から○ km」はただの数字に見える。push の前に、出す差分とコミットメッセージを目で読み、距離・到達時間・場所や機器を特定できる説明・画面の写しに写り込んだ位置や名前が無いかを見る
- **作者とコミッターのメールアドレスは、push の前に両方見る。** `git log --format='%ae %ce' origin/main..HEAD`（送る範囲に合わせて読み替える）。作者だけ見ていると、コミッターの欄に残った値を見落とす。git の設定でリポジトリの置き場所ごとに名前とアドレスを切り替えている（`includeIf` 等）なら、**その条件から外れた場所に clone・写しを置くと、切り替わらずに別のアドレスで記録される**。条件の外で commit するなら、その写しに `user.email` を明示する
- **GitHub のメールアドレスの保護（「Block command line pushes that expose my email」）には頼らない。** アカウントに登録済みのアドレスが出る push を拒む仕組みで、**登録していないアドレスは検査しない**
- **見つかったら、出すものを直す。** 既に push した履歴の中にあるなら、直すだけでは消えない —— 手を止めてユーザーへ報告する（履歴の書き換えはユーザーが決める）

### 履歴を書き換えて force push するとき

ユーザーが履歴の書き換え（`git filter-repo` 等）を決めたら、**手元の作業コピーではなく、新しく取った bare clone を起点にする。**

- **理由**: `git log @{u}..` が 0 件でも、手元がリモートより古くないことは保証されない。fetch していない作業コピーでは `@{u}` 自体が古いままなので、リモートが先行していても気づけない。手元を起点に書き換えて force push し、リモートにだけあったコミットを複数のリポジトリで巻き戻した例がある。手元に無い ref（取っていないタグ・他の端末で作ったブランチ）も取りこぼす
- 手順（実際にこの順で通した）:
  1. **作業の前に、対象の全リポジトリの bare clone をバックアップとして取る。** 巻き戻したときの唯一の復旧手段になる
  2. 書き換えは、新しく取った bare clone（`git clone --bare <リモートの URL>`）に対して行う。**取った時点の各 ref の SHA を控える。** `git filter-repo` は書き換えの後に `origin` を外すので、push 先の URL は明示する。push する ref はその clone の ref を列挙して明示し、`git push --force-with-lease=<ref>:<控えた SHA> <リモートの URL> <ref>...` の形で、取った後にリモートへ入ったコミットを巻き戻さないようにする（`--mirror` は手元専用のブランチまで公開するので使わない）。**force push の前に、push する ref の一覧をユーザーへ提示して承認を得る**
  3. push の後、各作業コピーを追従させる。**先に、未コミットの変更・リモートに無いコミット（手元の `git log` を、書き換え前に取ったバックアップと比べる）・stash・手元専用のブランチが無いかを確かめる。** 付け替えは下の箇条のとおり `git reset --keep` で行う（未コミットの変更とぶつかれば止まる）。**`--keep` も `--hard` も、付け替える前の手元のコミットは黙って外す** —— 手元にしか無いコミットを守るのは、この確認だけ
  4. 最後に**新しく clone し直して**、消したい値が消えたことを確かめる（作者とコミッターの欄も `git log --all --format='%ae %ce'` で見る）
- 手元専用のブランチも書き換えるなら、bare clone へ `git fetch <手元のリポジトリ> 'refs/heads/*:refs/heads/*' 'refs/tags/*:refs/tags/*'`（強制なし）で取り込み、`git filter-repo` を `--force` で走らせる
- 手元の付け替えは、作業ツリーのあるものは `git reset --keep <新>`、無いものは `git update-ref <ref> <新> <旧>`。**付け替える対象は `git for-each-ref` で `refs/heads` 以外も全部数える** —— 手で作った追跡用の ref が古い履歴を握ったまま残り、最後の検査で初めて気づいた例がある
- `--replace-text` は、表に書いた順ではなく**文字どおりの置き換えを全部当ててから正規表現を当てる**（配布先で踏んだ挙動。版によって変わりうるので、手順 4 の確認で消し残しを見る）。片方がもう片方の部分文字列になる置き換え（長い番号とその一部の短い番号など）は、両方を正規表現にして順序を保つ
- 同じ入力の履歴に同じ mailmap を当てれば、出てくるコミットの SHA は再現する（作業コピー側を別に書き換えても、リモートと SHA が一致する）
- 長いパスを含むリポジトリは、作業ツリーへ取り出すとき（手順 4 で clone し直すときなど）に `git -c core.longpaths=true clone` でないと取り出せないことがある（Windows）
- 置き換えの表には消したい実際の値が入るので、表や実際に通したコマンドの控えはリポジトリの外（スクラッチの領域）に置く

## 読んではいけないものは、スクリプト越しでも読んだことになる

プロジェクトによっては、Claude が中身を読んではいけない資料がある（未マスキングの受領データ、個人情報を含む実データ等）。
**どのパスがそれに当たるかは、プロジェクトの `CLAUDE.md` かユーザーの指示で決まる。** 書かれていない場合でも、
受け取ったままの実データを見つけたら、読む前に確かめる。

**`Read` を使わなければ読んでいない、ではない。** スクリプトに処理させても、**その標準出力に本文が出れば、
会話とターミナルに残る**（マスキング漏れを探すスクリプトが、見つかった行をそのまま標準出力へ出し、
数百行分の本文が会話へ流れ込んだ例がある）。

読んではいけないパスを対象にスクリプトを走らせるときは、次を守る。

- **本文を出力しない。** 出すのは件数・真偽のような、**中身を復元できない値**だけにする。
  一致した行を確認のために出す、という作りにしない
- **出力先をファイルにしても同じ。** そのファイルを読めば会話に入る。読まずに済む形（件数だけ受け取る等）にする
- **ファイル名・フォルダ構成の一覧・ハッシュは「要約した値」に数えない。** 名前には業務情報・所有者・
  実在する人や物の名前が入ることがあり、ハッシュも値域の狭い情報（電話番号・社員番号など）なら
  総当たりで元に戻せる。**出してよいかは、中身とは別に確かめる**
- **探索の過程でも入らない。** `find` / `Glob` / `ls` を広く掛けると、許可外のパスが結果に出る。
  **探索するパスを明示的に絞る**

**許可はユーザーから、都度・パス単位で受け取る。** 「あるフォルダが許可された」は「隣のフォルダも
許可された」を意味しない。**迷ったら読まずに確認する。**

## セキュリティ対応プロトコル

セキュリティ問題発見時:
1. 即座に停止
2. **security-reviewer** エージェントを使用
3. CRITICAL の問題はすべて修正してから続行
4. 漏洩したシークレットをローテーション
5. コードベース全体で類似の問題を確認
