# ドキュメント客観レビュー

## 概要

**ドキュメントを更新した場合、および利用者向けの文字列（UI 文言・データファイルの `description` 等）を新規作成・更新した場合**、対象箇所にエージェントで客観レビューを実施する。
目的: 技術的すぎないか・過剰でないか・初見の読み手に伝わるか・制作過程が漏れていないか・実装と乖離していないかを検証する。

**対象は「ドキュメント」に限らない。** 型定義が「概要を書く場所」と定めたフィールドに実装の作業経緯を書いてしまう事故は、仕様書や README と同じ穴で起きる（下記「データファイル・UI 文言特有の観点」）。

## 実施タイミング

**ドキュメント更新・該当文字列の作成/更新の直後、コミット前確認の前**。指摘があれば該当箇所に戻る。

## エージェント構成

- 更新規模が小さい場合（1 ファイル・数行の追記）: `doc-objectivity-reviewer` 1 エージェント
- 更新規模が大きい場合（複数仕様書・README 大幅改訂・CLAUDE.md 追記）: `doc-objectivity-reviewer` + `code-explorer` の並列 2 エージェント（後者は「初見の開発者視点」で追加観点を担当）

`doc-objectivity-reviewer` の定義はプロジェクトの `.claude/agents/` に配置する。

## レビュー観点

- **読者が誰か明示されているか**: 一般利用者向け / 開発者向け / 特定機能を触る人向け 等
- **前提知識のない読み手が理解できるか**: 過度な略語・専門用語の初出説明はあるか
- **実装との乖離がないか**: パラメータ値・関数名・行番号・ファイル名の正確性
- **冗長でないか**: 同じ内容が複数箇所に重複していないか（重複は単一情報源へ集約する候補）
- **技術的すぎないか**: 「実装の内部詳細」と「読者が知るべき挙動」の粒度が分離されているか
- **過剰でないか / 情報量が適切か**: 実装の複雑度・機能の重要度に対して分量が釣り合っているか
- **制作過程が漏れていないか**: 「ご要望どおり」「前版と違い」「ご指定により X は使っていません」など、読者の行動ではなく**その文書がどう作られたか**を語る記述が残っていないか。制約は成り立ちとして説明せず、手順・既定値・用語選びそのものに反映する。読者に守らせる禁止指示（「X は使うな」）と、判断を再現するために置いた設計根拠（`理由:` `根拠:` の類）はこれに当たらない
- **仕様書相互の整合性**: 別の仕様書と食い違う記述はないか

## データファイル・UI 文言特有の観点

`description` 等のメタデータフィールドや UI 表示文言は「その機能を初めて触る利用者」向けで、ドキュメントよりさらに読者の予備知識を仮定できない（実値との一致は [comment-integrity.md](./comment-integrity.md)「UI 説明文と実データの照合」の担当。ここで見るのは伝わりやすさと作業経緯の漏れ）:
- 会話・作業経緯に由来する語（作業フェーズ名・スコープ縮小の弁明・「ご要望どおり」等）が残っていないか
- **フィールドの用途に沿っているか** — 型定義のコメントが「何を書く場所か」を定めているなら、それに従っているか
- 実装上の妥協・簡略化・データの網羅範囲（「◯件のみ収録」「概算」「代表値」等）は、利用者向けフィールドではなく開発者向けの記述側に書かれているか。**利用者向けフィールドに書いてよいのは、対象そのものを説明する事実だけ**

## README 特有の観点

README は「一般利用者・フォーカー・貢献者への導線」であることを念頭に:
- 実装内部の詳細（プロジェクト構成ツリー・パラメータ値等）が入り込んでいないか
- 詳細は仕様書配下へリンク委譲されているか
- 開発者専用の情報（デプロイ手順・利用規約制限等）が混入していないか

## 出力形式

```
[レベル] [ファイル:節/行] 見出し
- 記述の該当箇所
- 何が伝わりにくいか / 何が実装と食い違うか
- 修正方針の候補
```

レベルは CRITICAL（誤情報・法的リスク）/ HIGH（読み手が誤解する）/ MEDIUM（冗長・重複・過剰な詳細・制作過程の漏れ）/ LOW（表現改善余地）。
