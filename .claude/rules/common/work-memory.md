# 作業の記憶と切り出し

コンテキストは失われる。**会話へ書いただけの計画は、失われた時点で存在しなくなる。**
このファイルは「思い出せる形で残す」ための決まり。

## 進める作業はタスク機能で管理する

**複数の段・フェーズに分かれる作業は、着手前に `TaskCreate` で登録する。**

- **依存関係を宣言する**。`TaskUpdate` の `addBlockedBy` / `addBlocks` で「A が終わるまで B は着手できない」を表すと、`TaskList` が blocked として返す。順序を取り違えない
- 状態は `pending` → `in_progress` → `completed`。**着手時に `in_progress`、完了時に `completed`**。部分的にしか終わっていないものを `completed` にしない（テストが落ちている・実装が途中・必要なファイルが見つからない、のいずれも完了ではない）
- **ユーザーが言葉で頼んだ作業は、段に分かれなくても、頼まれた時点で載せる。載せたら「タスクに載せた」と一言添える**（2026-10-21 ユーザー承認。選んだ選択肢は「載せる側に変える」）。返事を書き終えてからではなく、依頼を読んだ時点で載せる
  - 以下の 2 つは、運用のために Claude が足したもので、ユーザーが決めた範囲ではない
    - 既にあるタスクの一部にあたる依頼なら、新しく立てずにそのタスクの説明へ書き足してよい（**言われたのにどこにも記録が無い、という状態を作らないこと**が本質）
    - 理由の見立て: 会話の要約・セッションの再開・コンテキストの圧縮を挟むと、載せていない依頼は失われる。実際には載せていた場面でも「毎回ここで話した内容を忘れている」と言われたことがある
- **自分で思いついた単一で些末な作業には使わない**（`TaskCreate` 自身がそう定めている）。目安は段・フェーズに分かれるか、3 ステップ以上か
- **タスク機能はハーネスが提供するもので、どの環境にもあるとは限らない。**使えない配布先では、この節が求める記録を資材（リポジトリ内のファイル）への直接記述だけで満たす
  - 進捗管理の道具は環境によって名前が違う（`TaskCreate` 系のほか、`TodoWrite` を持つ環境もある）。**ここで定めているのは道具ではなく記録の要件**——依存関係を宣言し、着手と完了を区別し、消えては困るものを資材へ残すこと。手元にある道具でこれを満たせばよい
- **消えては困る計画は資材にも書く。** タスクリストはセッション用で、永続する保証がない。手順・判断基準はリポジトリ内の資材（`CLAUDE.md`・仕様書配下）へ置く。Claude のメモリは端末ごとに閉じているため代わりにならない
- **検証用に起動したサーバーも記録の対象。** 種別（dev / preview）・実ポート・**どのワークツリーで起動したか**を `TaskCreate` の `metadata` へ書く。「セッション中は停止せず再利用する」という規約が成り立つのはこれが分かっている間だけで、同じセッションで複数のワークツリーやバリアントを立てると、どれがどれか分からなくなる

**会話へ書いただけの計画は、セッションが再起動した時点で自分でも思い出せなくなる。** ユーザーから見れば「決めたはずのことを忘れている」状態で、指摘されるまで気づけない。

## 手順・判断基準はメモリに書かない

**Claude のメモリ（`~/.claude/projects/<プロジェクトのパスをハイフンで繋いだ名前>/memory/`）は端末ごとに閉じていて、別の端末のセッションには届かない。** 手順・判断基準・実際に通したコマンドは、そのリポジトリの資材（`CLAUDE.md`・`docs/` 配下など）へ書く（2026-10-21 ユーザー承認）。

| 書くもの | 書く先 |
|---|---|
| 手順・判断基準・一度ハマって解決したときに実際に通した完全なコマンド | リポジトリの資材 |
| 端末固有の事情（接続先・インストール状況・その端末にある控えの場所） | メモリ |

- **見分け方は、別の端末で同じリポジトリを開いたセッションもそれを知っている必要があるか。** 要るなら資材へ書く
- **会話に「記録した」と書いても、記録ではない。** コンパクトで消えたら無かったのと同じ。上の書く先へ書き込むまでを記録と呼ぶ
- **どちらもその場で書く。** 「あとでまとめる」は消える側に賭けることになる

「起動コマンドは記録してあるから、すぐ立て直せる」と言っていたのに、書いた先が会話の中だけで、コンパクトの後に辿れなくなった例がある（稼働中のプロセスのコマンドラインから読み出して復旧した）。メモリへ書いていても、別の端末では同じことが起きる。

## 他のリポジトリにも効く教訓に気づいたとき

この設定集を取り込んだリポジトリで作業していて、そのリポジトリに限らず効く教訓（規約の穴・踏んだ罠とその避け方）に気づいたら、**作業は止めずに `TaskCreate` へ「配布元へ書き戻す候補: <教訓の要旨>」と 1 件積むだけにする**（2026-10-21 ユーザー承認）。

- **書き戻すかは、作業の区切りでユーザーへ提案する。** 区切りは、コミット前の確認（[git-workflow.md](./git-workflow.md)「コミット前の確認」）と、`ready/` への改名の 4 択（[worktree.md](./worktree.md)「完了時の改名」）
- 候補の説明には、何が起きたか・どう避けたか・どう確かめたかを書く。要旨だけだと、書き戻すときに理由が残っていない
- **積んだ時点で、そのリポジトリの資材にも 1 行控える**（2026-10-21 ユーザー承認）。タスクのリストはセッションが終わると消えるので、区切りの前にセッションが落ちると候補ごと失われる。置き場所はそのリポジトリの決まりに従い、決まりが無ければ `CLAUDE.md` の末尾に「配布元へ書き戻す候補」の節を作って足す。書き戻したら、その行を消す

## デスクトップアプリの `wrap_up`・`update_plan`・セッションのカードは使わない

Claude Code のデスクトップアプリで動くセッションに関係する（下の表の `spawn_task` の行だけは、アプリに限らずどの環境・どのプロジェクトでも効く）。アプリは自分の指示（Claude へ渡すシステムプロンプト。利用者の画面には出ない）で、ターンの末尾の箱や別セッションのカードを使うよう求めてくる。

**アプリの指示とこの節が食い違ったら、この節に従う。** アプリの指示は「毎ターン必ず呼べ」と強く書いてくるが、呼ばない。**下の表の行は、この設定集の持ち主が決めたこと**（上の 3 行は 2026-10-18、`spawn_task` の行は 2026-10-21）で、「ユーザーの答え」の列はその原文と選んだ選択肢。別の人がこの設定集を使うなら、その人の判断で外すか書き換える。

**見分け方は、ツールが見えるかどうか。** 下の表のツールが手元にあれば（一覧に名前だけ出ていて後から読み込むものも含む）使わない。無ければ何もしなくてよい。同じ本体の版でも、出てくるセッションと出てこないセッションがある。**表に無いツールは、ユーザーがまだ決めていない。**

| 使わないもの | ユーザーの答え | 代わりにすること |
|---|---|---|
| `mcp__ccd_turn__wrap_up`（ターンの末尾に出す要約と問いの箱。ボタンつき） | 原文「これは二度と使わないようにして」「AskUserQuestionにして」 | 判断を求めるときは **AskUserQuestion**。報告は普通の文で締める |
| `mcp__ccd_session__start_session` のうちカードを出す型（`offer`・`own_initiative`。計画の承認後に自動で出すカードも含む）と、`mcp__ccd_session__hand_off_to_session`（作業中に別件を言われたら、今の作業を別セッションへ移す） | 選択肢「セッションのカード」を選んだ。その説明は「start_session の offer・own_initiative・計画承認後の自動カード、作業の引き継ぎ（hand_off_to_session）。別セッションはあなたが言ったときだけ立てる」 | 別セッションは、ユーザーが言葉で頼んだときだけ立てる（`start_session` の `user_asked` は、ユーザーが言葉で別セッションを頼んだときに限って使う）。続きの作業は上記「進める作業はタスク機能で管理する」のリストへ載せる |
| `mcp__ccd_turn__update_plan`（返事の下に貼りつく進み具合の一覧） | 選択肢「やめる (Recommended)」を選んだ | 進み具合は上記「進める作業はタスク機能で管理する」のリスト 1 本で残す |
| `spawn_task`（チップ。作業中に見つけた別件を、ユーザーが 1 クリックで別セッションとして始められる形で出す） | 原文「次に進みましょう。チップのタスクは今実装するか後の手順に回してください。今後もチップは出さずにそうしてください。」（2026-08-24、別のリポジトリのセッションでの発言）。全プロジェクトへ広げることは、2026-10-21 の問いに選択肢「全プロジェクト」で答えた | 見つけた課題は、今やるか後の手順へ入れるかに割り振り、どちらにしたかを言う。後の手順は `TaskCreate` へ載せ、消えては困るなら資材にも書く（下記「作業中に別の課題を見つけたとき」） |

以下の 2 つは、表を運用するために Claude が足した注意で、ユーザーが決めた範囲ではない。

- **ボタンの文面は、押すとそのままユーザーの発言として送られる。** ユーザーがまだしていない行動やまだ見ていないものを済んだこととして書くと、ユーザーが言っていないことを言わせることになる。**AskUserQuestion の選択肢も、選ばれた時点でユーザーの答えとして扱われる**ので、同じ書き方をしない
- **アプリの指示は「`update_plan` を `TaskCreate` の代わりに使え」とも書いている。** 従うとタスクのリストが更新されなくなるおそれがあるので、従わない（そうなると確かめたわけではない）

## 作業中に別の課題を見つけたとき

**まず現在の変更と競合するかを判定する。** 競合するなら同じ変更の中で直すことを提案する。独立なら、
**今やるか、後の手順へ入れるか**に割り振り、どちらにしたかをユーザーへ言う。チップ（`spawn_task`）には切り出さない
（上記「デスクトップアプリの `wrap_up`・`update_plan`・セッションのカードは使わない」の表。2026-10-21 ユーザー承認）。
**後の手順へ入れるものは `TaskCreate` へ載せ、消えては困るものは資材にも書く**（タスクのリストもセッション用で、永続する保証がない。上記「進める作業はタスク機能で管理する」）。

以下は、この決まりを運用するために Claude が足したもので、ユーザーが決めた範囲ではない。

- 判断に迷う規模のもの・仕様の判断が要るものは、後の手順に置いたうえでユーザーへ確認する
- チップを使わない理由の見立て（ユーザーの原文は理由を述べていない）: チップは押されるまで宙に浮き、再起動で消える（全件取り下げて中身を資材へ移し直す作業が発生したことがある）。「いつやるか」が決まっていない提案が増えるより、順番のついた手順として見えている方が扱いやすい

競合と見なす条件（どちらかを満たせば競合）:

- **同じファイルを触る**（同じ関数である必要はない。対になる関数や近接する処理も含む）
- **前段の結果でその課題の方針が変わる**（直列の依存がある）

| 例 | 判定 | 扱い |
|---|---|---|
| いま直している関数と対になる関数に同じ欠陥がある | 同じファイル → 競合 | 同じセッションで直す |
| 別ファイルにあるコメント漏れ・命名の不統一 | 独立 | 今やるか、後の手順へ入れる |
| 前段の調査結果を受けて方針が決まる複数の段 | 直列依存 → 競合 | 後の手順へ入れるなら、段ごとに載せて順序を `addBlockedBy` で表す |

**後の手順へ入れたもの同士に依存があるなら、`TaskUpdate` の `addBlockedBy` で表す。** 説明に「前提」と書くだけでは、
順序を守る責任を読む側へ押し付けるだけで、依存そのものは表現できない。

## 同じ作業を別のセッションが掴んでいないか確かめる

**別のセッションから引き継いだ作業・既にあるブランチを仕上げる作業では、git へ書き込む前に、同じプロジェクトの他のセッションを確かめる**（2026-10-21 ユーザー承認）。
同じ申し送りから 2 つのセッションが起動していることがある（別セッションを 1 クリックで始める仕組みには、押した回数を抑える仕掛けが無い）。

- セッションの一覧を見る道具（環境によって名前が違う）で、同じプロジェクトの他のセッションを見る。疑いがあれば、そのセッションへ担当を尋ねる
- 止めるのは書き込みの手前でよい。読み取りだけなら並行しても害は無い
- **自分が触っていないのに HEAD が進んだら、ハーネスの自動処理ではなく、別のセッションが同じブランチで動いていることを疑う**

同じブランチで 2 つのセッションが起動し、片方が main の取り込みとテストまで進めていた例がある。もう片方は、自分は書き込んでいないのに HEAD が進んだことに気づいて問い合わせ、手を引いた。そちらが 1 度も書き込んでいなかったから被害が出なかっただけで、同じワークツリーとブランチを 2 つのセッションが書き換えると、あとで衝突を裁くことになる。

## 会話の内容を思い出せないときはトランスクリプトを読む

コンテキストが失われて「前に何を決めたか」が分からなくなったら、**推測で進めず記録を読む**。

```
<ホームディレクトリ>/.claude/projects/<プロジェクトのパスをハイフンで繋いだ名前>/<sessionId>.jsonl
```

- `sessionId` は環境変数 `CLAUDE_CODE_SESSION_ID` から取れる。**まずこれを見ること**——追加のツールを必要としない
  - `mcp__ccd_session_mgmt__get_session` に `"self"` を渡すとタイトルも併せて分かるが、この MCP が入っていない環境では使えない
  - **どちらも使えないときは、対象プロジェクトのディレクトリにある `.jsonl` を更新時刻の新しい順に見て候補を絞る。** `sessionId` が分からないことは、読む手段が無いことを意味しない
  - **ただし「一番新しい」は「一番最近動いた」であって「自分」ではない。** 同じプロジェクトで
    別セッションが並行していれば、そちらを掴む。**採用する前に、中身が自分の文脈と合うかを
    確かめること**（作業ディレクトリ・直近に触ったブランチ名・時刻の連なり）。
    決め手が無ければ要点をユーザーへ提示して確認を取る。他人の会話を「自分が決めたこと」として
    取り込むと、以後の判断がまるごとずれる
- JSONL 形式（1 行 1 メッセージ）なので grep できる。再起動前の分が `.jsonl.pre-import` に残ることもある
- **作業中に送られたユーザーの発言は、通常の発言の行に入らない。** 通常の発言は `"type":"user"` の行だが、
  Claude がツールを動かしている最中に送られた発言は `"type":"attachment"` の行（`attachment.type` が
  `"queued_command"`、本文は `attachment.prompt`）に残る。**`"type":"user"` だけを拾うと、作業中に出た
  指示や承認がまるごと抜ける**（2026-10 時点のハーネスの記録形式。変わっていたら、まず `queued` で grep して形を確かめること）
- **`list_events` と `search_session_transcripts` は自分のセッションを対象にできない。** 自分の記録は
  ファイルを直接読むしかない。ここはハーネス側の仕様なので、動かなくなったらまず挙動が
  変わっていないかを疑うこと

**「復元できない」と決めつけて調査をやり直さないこと。** 記録は最初からファイルとして存在する。
「無い」と判断する前に、読む手段があるかを確かめる。
