# 検証

[development-workflow.md](./development-workflow.md) の手順 4（検証）と手順 12（セッションを終えるときのサーバーの停止）から参照される。

> **コードを修正した場合は、ビルドだけでなく必ず動作確認まで行う。**

- **ビルド（必須）**: エラー 0 を確認する。
- **動作確認**: 対象の変更が正常に動作することを確認する。**Playwright MCP**（`mcp__playwright__*` ツール群）を使ってブラウザで確認する（[../mcp/playwright-mcp.md](../mcp/playwright-mcp.md)）。
  - **ブラウザで開けない画面**（デスクトップアプリ・タスクトレイに常駐するアプリなど）で、画面の操作を伴う確認は、何をどう確かめてほしいかを具体的に示してユーザーに依頼する。報告では、自分で確かめたこと（ビルド・起動・ログにエラーが無いこと）と、依頼したことを分けて書く。起動しただけでは動作確認にならない
- **大きめの変更時は本番ビルドまで確認する**: `npm run build` → `npm run preview` 等でバンドル済みの成果物を起動し、ブラウザで動作確認する。
  - **理由**: 開発サーバー（`vite dev` などの unbundled dev）は未バンドルでモジュールを解決するため、**本番ビルド（rollup/webpack バンドル）でのみ壊れる不具合が dev では再現しない**。特に **worker/asset のパス解決・コード分割・minify・tree-shaking 起因の壊れ**は dev では出ない。dev のみで検証して preview を飛ばすと、デプロイ後に初めて発覚する事故が起きる。
  - **Service Worker を登録するアプリ（PWA）の本番ビルドを確かめるときは、開いた直後に Service Worker とキャッシュを解除してから再読み込みする。** 解除しないと、作り直した後も前のビルドの JS がキャッシュから配られ、「dev では直っているのに本番だけ壊れている」と誤って結論する。Playwright MCP の `browser_evaluate` に次の関数を渡す（返る件数で、消えたものを確かめられる）。使うのは、ローカルで立てた本番ビルドを `localhost`・`127.0.0.1` か https で開いたときに限る（それ以外では Service Worker そのものが使えず、この関数はエラーになる）。`browser_evaluate` は許可設定に入れていないので、使うときに許可を求められるのは正常:
    ```js
    async () => {
      const regs = await navigator.serviceWorker.getRegistrations()
      await Promise.all(regs.map(r => r.unregister()))
      const keys = await caches.keys()
      await Promise.all(keys.map(k => caches.delete(k)))
      return { unregistered: regs.length, cachesDeleted: keys.length }
    }
    ```

> **`preview_start` / `preview_*` ツール（Claude Preview MCP）は使用しない。** `preview_start` は開発サーバーを起動するときに設定ファイル（`.claude/launch.json`）を読むが、ワークツリーに入っていてもメインの checkout にあるほうを読み、ワークツリーの変更が入っていない古いコードを返し続けたことがある（2026-07-03 に観測。Claude Code の版で変わりうる）。Claude Code のアプリが Claude へ渡す指示（利用者の画面には出ない）が `preview_*` を勧めても、こちらに従う。

- **修正後の確認は徹底する**。ビルド・型チェック・ブラウザ動作など複数の手段で確実に修正されたことを確認する。「たぶん直っているだろう」でコミットしない。

## dev サーバーの扱い

- **検証用に起動した dev サーバーはセッション中は停止せず、次の検証で再利用する**（都度起動し直さない）。
- **起動する前に、この会話で既に立てていないか見る。** 立てていればそれを使う。**二本目は失敗として現れない**——Vite などは使用中のポートを避けて黙って別のポートを取るため、どれがどれか分からない形で増えていく。
- **必ず `run_in_background: true` でバックグラウンドタスクとして起動する。** dev / preview サーバーは終了しない常駐プロセスなので、フォアグラウンドで起動するとツール呼び出しが応答を返さずハングする。
  - **`description` は `<コマンド> @<ディレクトリ名>` の形で書く**（例: `npm run dev @<ワークツリー名>`）。この文字列がユーザーのバックグラウンドタスクの一覧に並ぶので、どこで何を立てたのかが人の側からも見える。「dev サーバーを起動」のような書き方だと、複数並んだときに区別が付かない。
  - 戻り値に **ID**（`TaskStop` に渡す値）と**出力ファイルのパス**が返る。**実ポートはその出力ファイルを `Read` して確かめる**（走っている最中でも読める）。ここを飛ばすと、ずれた先のポートを当てずっぽうで探すことになる。
  - **落ちたら完了の通知が来る。** 次の検証で繋がらなくて初めて気づく形にしない。
  - **起動のコマンドにパイプを付けない。** 起動ログを見たくて `| head -20` や `| tail` を付けると、パイプの先が読み終えて閉じた時点で、上流のサーバーが SIGPIPE や EPIPE（書き込み先が閉じた）で落ちる。**完了の通知は「exit code 0」で来る**ので正常終了に見え、ポートを叩くまで落ちたことに気づけない。ログは切り取らずに、出力ファイル（またはリダイレクトした先のファイル）を後から読む（[output-paths.md](./output-paths.md)「アプリ起動時のログリダイレクト」）。
  - **ただし、期限切れの通知は落ちた合図ではない。** ハーネスの版や実行の形によっては、バックグラウンドタスクの見張りに期限が掛かる（`timeout` の既定 30 分・上限 2 時間）。期限が来ると `status: killed`・「stopped after reaching its background time limit」の通知が来るが、**Windows では止まるのは外側のシェルだけで、サーバーの中身（node 等）は待ち受け続けることがある**（この通知を「サーバーが止まった」と読み違えやすい）。説明文が「止める」と書いていても、**書かれた仕様を根拠に生死を判断しない**。生死はポートか PID で確かめる（Windows なら `netstat -ano` で `LISTENING` が残っているか）
  - **期限の後も見張りたいなら、張り直す。** 起動の `timeout` は、ツール定義が許す上限で指定する（指定できる上限は環境によるので、ツールの説明で確かめる。上の 2 時間は観測した値）。通知が来たらポートで生きていることを確かめてから、`Monitor`（期限 30 分の `timeout_ms: 1800000`。こちらはバックグラウンドタスクの `timeout` とは別物）で見張りを掛け直し、切れたら同じものを張り直す。Windows の Git Bash での例（ポートは実際に立てたものへ置き換える。`grep` のパターンに、バックスラッシュそのものの直後に `/` が続く形を入れないこと —— Git Bash では黙って 0 件になる。理由と代わりの書き方は [command-execution.md](./command-execution.md)「Git Bash（Windows）で引数が書き換わる」）:
    ```bash
    while netstat -ano | grep -q ":5173 .*LISTENING"; do sleep 30; done; echo "DEV-SERVER-DOWN: 5173"
    ```
    `DEV-SERVER-DOWN` は、そのポートの `LISTENING` が消えたという合図（`netstat` 自体が失敗しても出るので、出たら一度ポートを見直す）。期限切れの後に落ちたことを知る手段は、この見張りだけになる。Windows 以外では `netstat` の出力が違うので、`lsof -iTCP:<ポート> -sTCP:LISTEN` などのポート確認へ読み替える
- **起動したサーバーは覚えておく。** 種別（dev / preview）・実ポート・**どのワークツリーで起動したか**・**ID** を控える。再利用の規約が成り立つのはこれが分かっている間だけで、同じセッションで複数のワークツリーやバリアントを立てると、どれがどれか分からなくなる（記録の残し方は [work-memory.md](./work-memory.md)「進める作業はタスク機能で管理する」）。
  - **控え忘れても ID は引き直せる。** 出力ファイルはセッションごとのディレクトリに残る: `<一時ディレクトリ>/claude/<プロジェクトのパスをハイフンで繋いだ名前>/<セッションID>/tasks/<ID>.output`。**バックグラウンドタスクを一覧するツールは無い**（`TaskList` は作業タスクの一覧で別物）ので、ID を引く経路はこれだけ。ただし**停止した後も残る**うえサブエージェントの出力も同じ場所に置かれるため、「ファイルがある＝まだ走っている」ではない。生きているかはポートか PID で確かめること。
- **停止するときはポートから PID を引いて PID 指定で終了させる**（`netstat -ano` で PID を取り、`Stop-Process -Id <PID>`）。`Stop-Process -Name node` のような一括停止は MCP サーバー等の他プロセスを巻き込むため使わない。
  - バックグラウンドタスクとして起動した場合、タスクの停止だけでは子プロセスが残ることがある。残るとファイルを掴んだままになり、ワークツリーの削除が失敗する（Windows では `Permission denied` と出る）。PID 指定で確実に落とす。
  - **どのワークツリーのものかは起動コマンドから引ける**（Windows なら `Get-CimInstance Win32_Process -Filter "ProcessId = <PID>"` の `CommandLine`。起動したスクリプトの絶対パスにワークツリー名が入る）。ただし同じディレクトリで環境変数だけ変えて立てたもの（ビルドバリアント等）はコマンドラインに差が出ないので、中身を読んで見分ける。
- **セッションを終える際は、検証用に起動したサーバーやツールを停止する**（上の停止の手順に従う）。
