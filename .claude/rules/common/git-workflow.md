# Git ワークフロー

## コミットメッセージ形式
```
<type>: <description>

<optional body>

Co-Authored-By: Claude <モデル名> <noreply@anthropic.com>
```

タイプ: feat, fix, refactor, docs, test, chore, perf, ci

コミットメッセージ末尾には必ず `Co-Authored-By` を付与する。**モデル名はその時作業している Claude モデルに合わせる**（ハーネスが指定するモデル名を使用する。特定モデルに固定しない）。
- 例（Sonnet 5 で作業時）: `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>`

**公開リポジトリでは、コミットメッセージ・作者とコミッターの欄にも個人情報を書かない。** メッセージは push した時点で公開され、ファイルを直しても履歴に残る（[security.md](./security.md)「公開する前に個人情報が無いことを確かめる」）。

## コミット前の確認

- **コミット前に必ずユーザーに確認を取る。省略しない**
- 何を・なぜ・どう直したかを簡潔に提示し、コミットしてよいか確認する
- 同一セッション内で別の修正のコミット許可をもらっていても、その修正を個別に確認していない場合は改めて確認する

## マージ・バージョン更新・プッシュ

これらは**実装フローの途中では行わない**。`release` スキル（`.claude/skills/release/SKILL.md`）の手続きに集約する。

- ファストフォワード可能な場合でも、必ずマージコミットを作成する（`git merge --no-ff`）。各機能・修正の単位を履歴上で明確に残すため
- バージョンはリリース 1 回につき 1 回だけ上げる（機能 1 本ごとではない）
- **バージョンフィールドを書き換えてよいのはリリース手続きの中だけ**（プロジェクトでバージョン番号を管理している場合）。ワークツリー内やマージ前のブランチでは変更しない
  - 理由: 複数のワークツリーを並行して進めていると、各セッションがワークツリー作成時点の古いバージョンを見て同じ番号を選んでしまい、正しく積み上がらない（例: 1.0.0 から 2 セッションが同時にパッチ修正すると、両方とも 1.0.1 を選んで最終的に 1.0.1 のまま残る）。リリースを 1 セッションに限れば、常に最新の値を見て +1 できる
  - バージョン表示箇所が複数ある場合は、可能な限り**単一の情報源**（バージョンファイル）から参照する形にし、手動での二重更新を避ける（例: Vite プロジェクトなら `define` でビルド時に注入する）
- 詳細は [development-workflow.md](./development-workflow.md)「リリース」を参照

## プルリクエストワークフロー

PR 作成時:
1. 最新コミットだけでなく、全コミット履歴を分析
2. `git diff [base-branch]...HEAD` で全変更を確認
3. 包括的な PR サマリーを作成
4. テスト計画を TODO として含める
5. 新しいブランチの場合は `-u` フラグでプッシュ

> 計画・TDD・コードレビューを含む完全な開発プロセスは
> [development-workflow.md](./development-workflow.md) を参照。
