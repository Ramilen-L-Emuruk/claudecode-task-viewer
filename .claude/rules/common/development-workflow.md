# 開発ワークフロー

> 本ファイルは [git-workflow.md](./git-workflow.md) を拡張し、git 操作前の開発プロセス全体を定義する。

## 機能実装ワークフロー

0. **調査・再利用**（実装前に必須）
   - **code-explorer** エージェントでコードベースを調査（既存の類似実装・パターンを検索）
   - **ライブラリドキュメントの確認**: 使用しているフレームワークの公式ドキュメントで API 動作を確認
   - **パッケージリポジトリの検索**（Maven/npm/PyPI 等）: 新しいユーティリティを書く前に既存ライブラリを確認。実績のあるライブラリを自前実装より優先
   - **参考実装の検索**: 問題の80%以上を解決するオープンソースプロジェクトを探す
   - 要件を満たすなら、ゼロから書くより実証済みのアプローチを採用・移植する

1. **計画を立てる**
   - **被害の見積もりを、方針を提示する前に裏取りする。** 「何が起きるか」を実装から確かめずに
     方針へ載せると、規模も優先度も対策の形も見当違いになる。とくに**並行処理・タイミングに
     関わる問題は、実測するか全経路を列挙する**まで断定しない（「同時に呼ばれる」と書く前に
     呼び出し元を全部数える、「こう壊れる」と書く前に壊してみる）
   - **課題ボードに書かれた見積もりは仮説として扱い、着手時に再検証する。** 積んだ時点の
     理解が古い・誤っていることがある（構造上の問題自体は実在するので、作業が無駄になるわけではない。
     ただし**被害の説明が違えば直す場所も変わる**）
   - **複数の段・フェーズに分かれる作業は `TaskCreate` で登録し、依存を宣言する**（[work-memory.md](./work-memory.md)）。
     会話へ書いただけの計画は、コンテキストが失われた時点で存在しなくなる
   - **planner** エージェントで実装計画を作成（3ステップ以上 or アーキテクチャに関わるタスク）
   - **architect** エージェントでシステム設計を検討（モジュール間の依存・レイヤー構成の判断時）
   - **code-architect** エージェントで具体的なクラス設計・API 設計を作成（新機能の場合）
   - 依存関係とリスクを特定
   - フェーズに分解
   - **ここで決めた範囲・深さ・粒度（「全て」等）を、後から自分の判断で狭めない。** 縮小が必要になったら実装の途中でも一旦手を止め、何をどこまで削るかを提示して確認を得る。**縮小した状態を先に成果物として出さない**

2. **TDD アプローチ**
   - **tdd-guide** エージェントを使用
   - テストを先に書く（RED）
   - テストを通す実装（GREEN）
   - リファクタリング（IMPROVE）
   - カバレッジ80%以上を確認
   - ビルド失敗時: **build-error-resolver** → 必要に応じて言語固有のビルドエラー解決エージェントにエスカレーション（詳細は `rules/java/agents.md` 等）
   - 反復的な修正-検証サイクルが必要な場合: **loop-operator** エージェントを使用

3. **コードレビュー**（並列実行を推奨）
   - コード記述直後に **reviewer** + **code-reviewer** エージェントを並列使用
   - フレームワーク固有の変更: フレームワーク固有のレビューエージェントを追加（詳細は言語別ルール、例: `rules/java/agents.md` の `java-reviewer`）
   - セキュリティ関連のコード: **security-reviewer** エージェントを追加
   - コメント・ドキュメンテーションコメントの変更: **comment-analyzer** エージェントを追加
   - CRITICAL・HIGH の問題を修正
   - 可能なら MEDIUM の問題も修正

4. **品質向上**（レビュー後・コミット前）
   - **code-simplifier** エージェントでコードのシンプル化を検討
   - **silent-failure-hunter** エージェントでエラーハンドリングの網羅性を検証
   - **refactor-cleaner** エージェントでデッドコード・未使用 import を整理
   - パフォーマンス懸念がある場合: **performance-optimizer** エージェントを使用

5. **敵対的レビュー**（品質向上後・コミット前。**全変更が対象。小規模修正でも省略しない**）
   - **小規模変更**: `adversarial-reviewer` 1 エージェント
   - **中規模変更**: `adversarial-reviewer` + `silent-failure-hunter` の並列実行
   - **大規模変更**: 領域別に `adversarial-reviewer` を複数並列 ＋ `meta-reviewer` でメタレビュー
   - 詳細は [adversarial-review.md](./adversarial-review.md) を参照
   - 指摘があれば実装に戻る。修正後に再度敵対的レビューを実施する。
     **ただし無条件に繰り返さない**——収束しない場合の打ち切り条件は
     [adversarial-review.md](./adversarial-review.md)「巡回をどこで打ち切るか」に従う
   - **レビューは「見た目・体感」を検出しない。** エージェントが見るのは記録が残るか・経路が漏れていないか・対称かであって、操作したときの手触りは見ない。表示の乱れ・引っかかり・待たされる感じは人が触るまで出てこないため、**何巡回しても動作確認の代わりにはならない**

6. **ドキュメント更新**（コードの変更に応じて。対象に変更がなければスキップ）
   - 仕様書・README・CLAUDE.md・コード内コメントを同一コミットで更新する
   - 詳細は [comment-integrity.md](./comment-integrity.md) を参照

7. **ドキュメント客観レビュー**（ドキュメント、または利用者向けの文字列（UI 文言・データファイルの `description` 等）を更新した場合）
   - `doc-objectivity-reviewer` エージェントを使用
   - 詳細は [doc-objectivity-review.md](./doc-objectivity-review.md) を参照
   - 指摘があればドキュメントに戻る

8. **コミット**
   - 詳細なコミットメッセージ
   - Conventional Commits 形式に従う
   - 詳細は [git-workflow.md](./git-workflow.md) を参照
   - **プッシュはここでは行わない**（下記 10 に集約する）

9. **main の取り込みとリリース待ちへの登録**
    - ワークツリー内で `git merge main` を実行し、先行分を取り込む。放置すると乖離が積み上がる
      - 取り込むのは**ローカルの `main`** でよい。`origin/main` がさらに先行していることもあるが（別クローン・別環境でリリースが完了した場合）、**その差はリリース手続きの着手前チェックで解消されるため、実装セッションが追いかけない**（`main` を進める操作をしないこと）
    - コンフリクトを解消したら検証を再実行する。**解消が実質的なコード変更を伴った場合は敵対的レビューをもう 1 度回す**
    - **ブランチ名を `worktree/*` から `ready/*` へ改名する前に、ユーザーに確認を取る**（改名は「この内容でリリースしてよい」という宣言にあたる）
      - 確認は **AskUserQuestion** で 4 択を提示する（**1.** リリース待ちのみ / **2.** リリース待ち＋片付け / **3.** 続けてリリース / **4.** まだ改名しない）。ユーザーの発言が既にどれかを一意に指している場合は提示を省略してよいが、**コンフリクト解消を伴った場合、および伴ったか判然としない場合は省略せず差分を提示して確認する**。各選択肢の動作と省略条件の詳細は [worktree.md](./worktree.md)「完了時の改名」
      - **4 択を出すかどうかは「自分（Claude）が作業を完了したと判断したか」で決める。** 追加のフェーズ・修正が続く見込みがあるうちは出さず、コミットのたびに聞き直さない。逆に完了と判断したなら、ユーザーの意向を先読みして自主的に省略しない
    - **ここで実装セッションは終了。** マージ・バージョン更新・プッシュを自発的に行わない

10. **リリース**（**ユーザーから明示的に指示があったときのみ**）
    - `release` スキル（`.claude/skills/release/SKILL.md`）を使う。main へのマージ・統合後の検証・バージョン更新・プッシュ・ワークツリー掃除までを一括で行う
    - **e2e-runner** エージェントで重要なユーザーフローを検証（Web 画面に影響する変更の場合）
    - **doc-updater** エージェントで関連ドキュメントを更新（API・設定変更を含む場合）
    - 全自動チェック（CI/CD）が通過していること

> 8〜9 と 10 を分けている理由: 複数セッションが並行して作業する場合、main が共有資源の奪い合いになる。main を書き換える操作をリリース手続きに集約し、その主体を常に 1 つに限ることで、実装セッション間の順番調整を不要にする。

## ユーザーからの合図

ユーザーが特別な言い回しを覚える必要はないが、次の意図は取り違えないこと。

| ユーザーの言葉 | 意味 |
|---|---|
| 「コミットして」 | 手順 8〜9 のうちコミットと main の取り込みまで。`ready/` 改名を持ち出すかどうかは、[worktree.md](./worktree.md)「完了時の改名」の「確認の出し方」の基準に従う |
| 「リリース待ちに入れて」 | `ready/` へ改名し、実装セッションを終える（ワークツリーも片付けるなら選択肢 2）。**4 択の提示は省略してよい**（コンフリクト解消を伴った場合を除く。下記） |
| 「リリースして」 | `ready/` へ改名し、続けて手順 10（リリース）へ進む。**4 択の提示は省略してよい**（同上） |
| 「これで十分」 | レビューの反復（敵対的レビュー・ドキュメント客観レビューのいずれも）を打ち切り、その時点の内容で確定する |
| 「まだ直したい」 | `ready/*` を `worktree/*` へ戻して作業を再開する（push 前ならいつでも巻き戻せる）。**改名前に言われた場合は選択肢 4** —— 改名しないだけで、巻き戻し操作は要らない |

**発言から選択肢が一意に決まっても、コンフリクト解消を伴った（または伴ったか判然としない）場合は 4 択を省略せず、差分を提示してから確認する。** 発言した時点と実際の中身が食い違っているため。

**push するまでは、いずれの操作も引き返せる。** コミットも `ready/` 改名もローカルの操作にすぎない。「もう戻れない」と誤解させないこと。
