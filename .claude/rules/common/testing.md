# テスト要件

## テスト駆動開発

必須ワークフロー:
1. テストを先に書く（RED）
2. テストを実行 — 失敗することを確認
3. 最小限の実装（GREEN）
4. テストを実行 — 通過することを確認
5. リファクタリング（IMPROVE）
6. カバレッジ確認（下記「カバレッジの数字だけで品質を判断しない」）

## カバレッジの数字だけで品質を判断しない

**カバレッジは「通った行」しか数えない。** その行が何を保証しているかは見ない。だから
**実装側に仮置きが多いほど数字は高く出る**——どれも素直に通る行だから。

- 条件が決まるまでの仮置き（必ず通る分岐・固定値を返すスタブ）
- 未解決の箇所を埋めるプレースホルダ
- 型が合わないときのフォールバック（握り潰しに近い既定値）

**「カバレッジが上がった＝良くなった」で判断しない。** 上がった分が、確かめている範囲の増加なのか、
上のような仮置きの増加なのかを見る。**実装を壊したときにテストが落ちるかを測る指標
（ミューテーションテスト等）を使えるなら、そちらのほうが実態に近い。**

**高い数字は品質の証明にならないが、低い数字は未検証の範囲がある印として使える。** 数字を支えているのは
**落ちることを確かめたテスト**（確かめ方は下記「後から足す回帰テスト」。何も検証しないテストは
下記「テストのアンチパターン」）。

## テストで必ずカバーすべきエッジケース

1. **null** 入力
2. **空** の配列・文字列
3. **不正な型** の入力
4. **境界値**（最小/最大）
5. **エラーパス**（例外スロー）
6. **エンコーディング・文字種変換に関わる境界値**（全角・半角変換等）

## 後から足す回帰テスト

TDD（先に書いて落ちるのを見る）が守るのは新機能。**レビュー指摘やバグ修正で「後から」足す
テストには、落ちることを確かめる機会が無い。** 通ったことしか見ていないテストは、
**修正を戻しても通る**——つまり何も守っていない可能性がある。

- **修正を一時的に戻して、テストが落ちることを確認する。** 落ちなければそのテストは無意味。
  **戻し方は復元を機械的にできる手段を使う**（対象ファイルを別名で控えておいて上書きで戻す・
  パスと一意の印を付けた `git stash push -m <印> -- <パス>` で退避し、印から引いた SHA を `git stash apply` で戻し、印から番号を引き直して drop する等。印が引けなければ退避されていないので先へ進まない。stash は他のワークツリー・セッションと共有されるので、素の `git stash`・`git stash pop` は使わない。手順の全体は `release` スキルの手順 5）。手で書き戻すと、セッションが中断したときに
  「修正を戻した状態」が残る
  - **控えから戻すときは、更新時刻ごと戻さない。** 更新時刻まで写す方法（Python の `shutil.copy2` 等）で戻すと、
    ビルドツールが「ビルド済みの成果物の方が新しい」と判断して再ビルドせず、**壊したときの成果物を使い続ける**。
    「修正を戻したのにテストが落ちたまま」という結果を読み違えた例がある。中身だけを写して更新時刻を今にする
    （Python なら `shutil.copyfile` のあとに `os.utime(dst, None)`）
  - **落ちたことだけで満足しない。** 赤が出ても、それが期待どおりの理由とは限らない。壊す前・壊した後・戻した後の
    すべてで走らせ、**赤から緑へ実際に切り替わる**ところまで見る
  - **追記式のログを検索して判定するテストは、実行前の位置から後だけを読む。** 素で全文を検索すると、
    前の実行で自分が書いた行に当たり、検出器を丸ごと止めても緑になる。実行前にログの長さ（バイト数）を覚え、
    それ以降だけを読む。**位置が長さと等しい（まだ何も追記されていない）ときに読み飛ばしを省く作りにしない** ——
    いちばん普通の状態で全文を読むことになり、同じ症状が再発した例がある
- **確率的な検出になるテストは、検出率を実測して反復回数を決める。** 決めた数値と実測結果を
  テストのコメントに書く（「2 万回では 3 回に 1 回見逃したので 10 万回にした」）。
  あわせて**偽陽性が出ないこと**（実装が正しければ原理的に成功する）を明記し、
  **通ったことは保証ではなく反証の不在**だと書き添える
- **並行処理のテストで待ち合わせ（バリア・イベント）を使うなら、必ずタイムアウトを置く。**
  片側が assert で抜けたときにもう片側が永久に待つと、症状が「assert 失敗」ではなく
  **ハング**として出て、ランナーのタイムアウト頼みになり何が壊れたか読めない。
  **落ちるべきときに落ちないテストは、無いより悪い**
- **対象システムが持つ静的・グローバルな状態に触るテストは、他のテストと混ざる前提で書く。**
  テストランナーはクラス単位で並列に走ることが多い。自分が書いたものだけを対象に絞る
  （自分だけが使う目印を入れる等）。「自分しか書かない」を仮定すると、無関係な失敗として現れる。
  **下記「テストのアンチパターン」の「テスト間の依存（共有状態）」とは別物**——あちらは
  テストが自分で共有状態を作ることを禁じている。こちらは**対象側に元からある静的状態**に
  触らざるを得ない場合の守り方

## 時間帯に触るテストは、手元と CI の両方の時間帯で通す

CI の実行環境は UTC のことが多い。期待値を手元の時間帯でだけ作ってしまうと（時間帯を切り替えるブロックの外で
期待値を作る等）、手元では緑のまま CI でだけ時差の分ずれて落ちる。

- **コミットの前に、CI と同じ時間帯でも走らせる**（Node.js なら `TZ=UTC npm test`）。手元の実行だけでは CI を代表しない
- CI でテストが落ちるとビルドもデプロイも走らない構成では、**push は通っても本番は前の版のまま止まる**
  （2 版続けて止まっていたのに誰も気づかなかった例がある）

## 計測の結果には、狙った負荷を実際に踏んだ証拠を持たせる

**差の出ない条件で差が出なかったことを、良い結果と読まない。** 計測や比較の結果が「問題なし」「同じ」と出たとき、
それが「対象に問題が無い」のか「計測が差を拾えない条件だった」のかは、結果の数字だけでは区別できない。

- **上限に張り付いた計測は、検出の失敗であって問題の不在ではない。** 計測する仕組みそのものの上限（更新の間隔・
  タイムアウト・取得件数の上限など）にどの条件も張り付き、どこが律速しているかを切り分けられなかった例がある。
  余力（どこまで負荷を上げると崩れるか）を測っていなければ、「十分速い」とは言えない
- **確かめた方向が、差の出ない方向だけになっていないか見る。** 作りの違う 2 つの実装は、特定の方向・範囲でだけ
  結果が重なることがある。重なる方向だけを試して「一致した」と結論し、試していない方向では食い違っていた例がある
- **指標が狙った事象を拾える形かを確かめる。** まれに起きる重い 1 回は、全体に占める割合が小さいと
  平均や上位パーセンタイルの外に埋もれて「問題なし」と読める（全体の 2% 弱の事象は 95 パーセンタイルに現れない）。
  事象が起きた直後の 1 回を名指しで記録するなど、事象そのものを捉える指標を別に持つ
- **結果と一緒に、その負荷を踏んだ証拠を残す。** 基準の値（負荷なしの計測）・狙った処理が実際に走った回数・
  上限に張り付いていないことを、結果と同じ記録に入れる。証拠が欠けていたら、結論より先にそれを埋める

## テストのアンチパターン

- 動作ではなく実装の詳細をテストする
- テスト間の依存（共有状態）
- 検証が不十分（何も検証しないテスト）
- 外部依存のモックが不足

## 品質チェックリスト

- [ ] 全 public メソッドにユニットテストがある
- [ ] エッジケースをカバー（null、空、不正）
- [ ] エラーパスもテスト（正常系だけでなく）
- [ ] 外部依存にモックを使用
- [ ] テストが独立（共有状態なし）
- [ ] アサーションが具体的で意味がある

## テスト構造（AAA パターン）

Arrange-Act-Assert 構造を優先:
1. **Arrange**: テスト対象・入力データを準備する
2. **Act**: テスト対象の処理を実行する
3. **Assert**: 結果を検証する

具体的なコード例・テストフレームワークの構文は言語別ルール（例: `rules/java/testing.md`）を参照。

## トラブルシューティング

1. **tdd-guide** エージェントを使用
2. テストの分離を確認
3. モックが正しいか検証
4. テストではなく実装を修正（テストが間違っている場合を除く）
