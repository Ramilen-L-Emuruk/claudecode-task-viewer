# テスト要件

## テスト駆動開発

必須ワークフロー:
1. テストを先に書く（RED）
2. テストを実行 — 失敗することを確認
3. 最小限の実装（GREEN）
4. テストを実行 — 通過することを確認
5. リファクタリング（IMPROVE）
6. カバレッジ確認

## テストで必ずカバーすべきエッジケース

1. **null** 入力
2. **空** の配列・文字列
3. **不正な型** の入力
4. **境界値**（最小/最大）
5. **エラーパス**（例外スロー）
6. **エンコーディング・文字種変換に関わる境界値**（全角・半角変換等）

## 後から足す回帰テスト

TDD（先に書いて落ちるのを見る）が守るのは新機能。**レビュー指摘やバグ修正で「後から」足す
テストには、落ちることを確かめる機会が無い。** 通ったことしか見ていないテストは、
**修正を戻しても通る**——つまり何も守っていない可能性がある。

- **修正を一時的に戻して、テストが落ちることを確認する。** 落ちなければそのテストは無意味。
  **戻し方は復元を機械的にできる手段を使う**（対象ファイルを別名で控えておいて上書きで戻す・
  `git stash` で退避する等）。手で書き戻すと、セッションが中断したときに
  「修正を戻した状態」が残る
- **確率的な検出になるテストは、検出率を実測して反復回数を決める。** 決めた数値と実測結果を
  テストのコメントに書く（「2 万回では 3 回に 1 回見逃したので 10 万回にした」）。
  あわせて**偽陽性が出ないこと**（実装が正しければ原理的に成功する）を明記し、
  **通ったことは保証ではなく反証の不在**だと書き添える
- **並行処理のテストで待ち合わせ（バリア・イベント）を使うなら、必ずタイムアウトを置く。**
  片側が assert で抜けたときにもう片側が永久に待つと、症状が「assert 失敗」ではなく
  **ハング**として出て、ランナーのタイムアウト頼みになり何が壊れたか読めない。
  **落ちるべきときに落ちないテストは、無いより悪い**
- **対象システムが持つ静的・グローバルな状態に触るテストは、他のテストと混ざる前提で書く。**
  テストランナーはクラス単位で並列に走ることが多い。自分が書いたものだけを対象に絞る
  （自分だけが使う目印を入れる等）。「自分しか書かない」を仮定すると、無関係な失敗として現れる。
  **下記「テストのアンチパターン」の「テスト間の依存（共有状態）」とは別物**——あちらは
  テストが自分で共有状態を作ることを禁じている。こちらは**対象側に元からある静的状態**に
  触らざるを得ない場合の守り方

## テストのアンチパターン

- 動作ではなく実装の詳細をテストする
- テスト間の依存（共有状態）
- 検証が不十分（何も検証しないテスト）
- 外部依存のモックが不足

## 品質チェックリスト

- [ ] 全 public メソッドにユニットテストがある
- [ ] エッジケースをカバー（null、空、不正）
- [ ] エラーパスもテスト（正常系だけでなく）
- [ ] 外部依存にモックを使用
- [ ] テストが独立（共有状態なし）
- [ ] アサーションが具体的で意味がある

## テスト構造（AAA パターン）

Arrange-Act-Assert 構造を優先:
1. **Arrange**: テスト対象・入力データを準備する
2. **Act**: テスト対象の処理を実行する
3. **Assert**: 結果を検証する

具体的なコード例・テストフレームワークの構文は言語別ルール（例: `rules/java/testing.md`）を参照。

## トラブルシューティング

1. **tdd-guide** エージェントを使用
2. テストの分離を確認
3. モックが正しいか検証
4. テストではなく実装を修正（テストが間違っている場合を除く）
