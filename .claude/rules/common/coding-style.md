# コーディングスタイル

## イミュータビリティ（重要）

可能な限り不変オブジェクトを使用:

```java
// 悪い例: 可変オブジェクト
public class Config {
    private String name;
    public void setName(String name) { this.name = name; }
}

// 良い例: 不変オブジェクト
public class Config {
    private final String name;
    public Config(String name) { this.name = name; }
    public String getName() { return name; }
}
```

根拠: 不変データは隠れた副作用を防ぎ、デバッグを容易にし、安全な並行処理を可能にする。

## コア原則

### KISS（Keep It Simple）

- 実際に動く最もシンプルな解決策を選ぶ
- 早すぎる最適化を避ける
- 巧妙さより明快さを優先

### DRY（Don't Repeat Yourself）

- 繰り返しのロジックを共有メソッド・ユーティリティに抽出
- コピー&ペーストによる実装のドリフトを避ける
- 投機的でなく実際の繰り返しがあるときに抽象化を導入

### YAGNI（You Aren't Gonna Need It）

- 必要になる前に機能や抽象化を構築しない
- 投機的な汎用化を避ける
- シンプルに始め、圧力が本物のときにリファクタリング

## ファイル構成

多くの小さなファイル > 少数の大きなファイル:
- 高凝集・低結合
- 200〜400行が一般的、800行が上限
- 大きなクラスからユーティリティを抽出
- 型別ではなく機能・ドメイン別に整理

## エラーハンドリング

常にエラーを包括的にハンドリング:
- 各レイヤーで明示的にエラーを処理
- サイレントな空 catch ブロックを避ける（最低限ログ出力）
- 適切な例外型を使い分ける（checked vs unchecked）
- 外部データ（API レスポンス、ユーザー入力、ファイル内容）を信頼しない

## ログ設計

診断ログを二段（既定で無効な詳細ログ／常に残る致命ログ）に分ける場合:
- 不変条件違反・呼び出し規約違反は**必ず常に残る側**で記録する。詳細ログ側に書くと既定では何も残らないのに、コードは「ログに残しているから追える」と読める
- ただし常に残る側がプロセス間ロックやファイル I/O を伴うなら、**クリティカルセクション内・高頻度に呼ばれる経路では呼ばない**（ロック保持中に呼ぶと処理全体を数百ミリ秒単位で止めうる）

## 並行処理での待ち合わせ

条件変数（`wait`/`notifyAll`・`Monitor.Wait`/`PulseAll`・`condition_variable` 等）で待たせる場合:
- 待機側が前進できる状態へ**遷移させる経路は 1 つ残らず通知する**。1 つ漏れれば待機側は寝たまま起きず、処理が止まる
- ただし**状態を何も変えずに早期 return するガードは通知しなくてよい**。待機条件が変わっていないなら起こすべき待機者は存在しない

## 入力バリデーション

システム境界で常にバリデーション:
- Controller 層で全ユーザー入力を検証
- Bean Validation（`@NotNull`、`@Size` 等）を活用
- 明確なエラーメッセージで早期に失敗

## 命名規約

- 変数・メソッド: `camelCase`（説明的な名前）
- boolean: `is`、`has`、`should`、`can` プレフィックス
- クラス・インターフェース: `PascalCase`
- 定数: `UPPER_SNAKE_CASE`
- パッケージ: `lowercase`（ドット区切り）

## コードスメルの回避

### 深いネスト

ネストが積み重なったら早期リターンを優先。

### マジックナンバー

閾値・遅延・制限には名前付き定数を使用。

### 長いメソッド

大きなメソッドは明確な責務を持つ小さなメソッドに分割。

## コード品質チェックリスト

作業完了前に確認:
- [ ] コードが読みやすく、適切に命名されている
- [ ] メソッドが短い（50行以下）
- [ ] クラスが焦点を絞っている（800行以下）
- [ ] 深いネストがない（4段階以下）
- [ ] 適切なエラーハンドリング
- [ ] ハードコード値がない（定数または設定を使用）
