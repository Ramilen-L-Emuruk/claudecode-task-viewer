# MRレビュー（MR/PR + 課題管理チケット連携）

## 概要

自分が実装したコードのレビューではなく、**他者が作成した MR/PR**（GitLab・GitHub 等のコードホスティングサービス上のマージリクエスト／プルリクエスト）をレビューする際の手順。MR/PR の URL と課題管理チケット（Jira・Linear・GitHub Issues 等）の URL（またはどちらか）を渡されてレビューを依頼された場合に適用する。

MR/PR単体を読むだけでは「なぜその実装にしたか」が分からないことが多い。チケット側の実装方針・Exit Criteria・サブタスクの作業手順まで取得し、実装がそれを満たしているかを突き合わせるのがこのフローの核。

## 実施フロー

### 1. 情報収集

- MR/PR情報（タイトル・説明・差分ファイル一覧）を取得する。認証情報・API呼び出し手順はプロジェクト・利用サービスごとに確認する。
- 課題管理チケットを取得する。**親チケット**（背景・実装方針・Exit Criteria）と**サブタスク**（詳細な作業手順・個別のExit Criteria）の両方を確認する。サブタスクは結論欄が空でもコメントに経緯が残っていることがあるため、コメントも必ず確認する。
  - チケットのURLが渡されなかった場合は、MR/PRのタイトル・説明・ブランチ名（例: `feature/TICKET-123-xxx`）からチケット番号を抽出できないか確認する。抽出できなければユーザーに確認するか、チケットなしで実装コードのみを根拠にレビューを進める旨を明示する。
- ローカルに対象モジュールのリポジトリがあれば、`git fetch` で MR/PR のソース／ターゲットブランチを取得し `git diff base...head` で全差分を見る。ホスティングサービスの diff API より高速・正確。

### 2. 一次分析（自分で読む）

- 差分を読み、チケット記載の実装方針と実装が実際に一致しているか目視で確認する。
- 変更されたコードが依拠する既存コード（同一プロジェクト内の類似実装）と比較し、規約からの逸脱がないか確認する（例: 命名規則、既存ユーティリティの使い回し等）。
- ここで気づいた懸念は「仮説」として明文化しておき、後続のエージェントに検証させる。自分の直感だけで確定させない。

### 3. レビュー用ワークツリーの作成

サブエージェントは呼び出し時点の作業ディレクトリの状態しか見えない。MR/PRのブランチをそのまま読ませたい場合は、独立したワークツリーとして展開してからエージェントに渡す（type は既存の `chore` を使う。レビュー専用の新しい type は増やさない）。

```bash
git worktree add -b worktree/chore/mr-review-<番号> .claude/worktrees/mr<番号>-review origin/<MR/PRのソースブランチ>
```

メインの自分はこのワークツリーで**読み取り専用の調査しか行わない**ため、[worktree.md](./worktree.md) の `EnterWorktree` で入る必要はない。ワークツリーの絶対パスをそのままサブエージェントへのプロンプトに含めれば十分。削除手順（`git worktree remove` → ブランチ削除）は [worktree.md](./worktree.md) に準じる。

### 4. 専門エージェントによる並列レビュー

MRレビューは「自分が書いたコードの敵対的レビュー」（[adversarial-review.md](./adversarial-review.md)）とは目的が異なり、他者が完成させたコードを複数の異なる観点から独立に検証する。**基本構成として次のエージェントを並列起動する**:

- **code-reviewer**: コード品質・セキュリティ・パフォーマンス全般
- フレームワーク固有のレビューエージェント（該当する場合。例: Java プロジェクトの `java-reviewer`）: 設計・アーキテクチャ・並行処理・レイヤー責務分離
- **adversarial-reviewer**: 実装からの裏取り、チケット仕様との整合性、エッジケース

変更が小規模（1〜2ファイルの軽微な修正）なら `adversarial-reviewer` 1エージェントに絞ってよい。大規模（アーキテクチャ変更・複数機能横断）なら [adversarial-review.md](./adversarial-review.md) の基準に沿って領域別に複数並列＋メタレビューを追加する。

各エージェントへのプロンプトには必ず次を含める:

- 対象ファイルの絶対パス（ワークツリー内）
- チケットの実装方針・Exit Criteriaの要約（具体的な合格基準を明文化したもの）
- 自分の一次分析で見つけた懸念点（「検証してほしい仮説」として明示し、断定しない）
- **「テストが green でも、テストフィクスチャ自体が実運用のデータ形式と乖離している可能性がある。実運用相当の既存フィクスチャ・設定ファイルと突き合わせて確認すること」という指示** — 新規実装が独自に発明したテストフィクスチャだけで検証されており、実データの形式的な違い（単純な完全一致を想定したテストと、実際はより複雑な記法を持つ本番データとの食い違い）が新設テストでは検出できない、という事故が実際に起きたため必須の観点とする

3エージェント以上を並列起動する場合は `run_in_background`（デフォルト）のまま一度に投入し、完了通知ごとに結果を確認する。

### 5. 結果の統合・裏取り

- 複数エージェントが独立に同じ指摘をした場合は確度が高いと判断してよい。**ただし保証されるのは結論の確度だけで、根拠が正しいかは別問題**。指摘を採用する前に、機構の説明が実装と合っているかを確認する（[adversarial-review.md](./adversarial-review.md)「メタレビュー」）。
- CRITICAL/HIGH判定でエージェント間に食い違いがある場合、または1エージェントのみが検出した重大指摘がある場合は、**自分でも実装ファイル・実運用相当のテストフィクスチャ等を直接確認して裏取りする**。エージェントの報告を鵜呑みにしない。
- 大規模変更で CRITICAL/HIGH が多数出た場合は `meta-reviewer` エージェントでの再検証も検討する。

### 6. 報告・投稿

- まずユーザーにこの場でレビュー結果を提示する。
- MR/PRへのコメント投稿は他者に見える行為のため、**ユーザーの明示的な承認を得てから**実施する（承認なしに投稿しない）。
- 投稿方法・文字化け対策等は利用サービス・プロジェクトごとに確認する。

### 7. 後片付け

レビュー用ワークツリーは、ユーザーに確認のうえで削除する（[worktree.md](./worktree.md) 削除手順）。

## 判定基準

[code-review.md](./code-review.md) の CRITICAL/HIGH/MEDIUM/LOW 基準をそのまま流用する。
