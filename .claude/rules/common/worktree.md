# ワークツリー運用

## 作成手順

`EnterWorktree(name: ...)` はブランチ名を自動変換してしまうため使用しない。
必ず以下の手順で行う。

```bash
# Step 0: メインの checkout 側でローカルの既定ブランチを最新へ
git pull

# Step 1: 正しいブランチ名でワークツリーを作成
git worktree add -b worktree/<type>/<name> .claude/worktrees/<name>

# Step 2: 作成したワークツリーに入る（path 指定で呼ぶ）
EnterWorktree(path: ".claude/worktrees/<name>")
```

**Step 0 を飛ばさないこと。** ローカルの既定ブランチが `origin` に遅れたまま切ると、後退した地点から作業を始めることになり、あとで作り直す手戻りになる。ワークツリー内からは `git pull` できないため、切る前にメインの checkout 側で済ませる。

type の種類: `feat` / `fix` / `refactor` / `docs` / `chore`

`worktree/` という接頭辞は**作業中**であることを表す。

### リリース待ちのブランチから派生させて次を積む

前の作業が `ready/*` でリリースを待っている間に、その上へ次の作業を積むときは、前のブランチを起点に指定して切る。

```bash
git worktree add -b worktree/<type>/<次の名前> .claude/worktrees/<次の名前> ready/<type>/<前の名前>
```

- **派生に要るのはブランチで、ワークツリーのディレクトリではない。** 前のワークツリーを「完了時の改名」の選択肢 2 で片付けていても、`ready/*` が残っていれば切れる
- **`ready/*` の上で直接続きを書かない。** `ready/*` は「いつリリースされてもよい状態」を表す（下記「完了時の改名」）。そこへ足した続きは、未完成のまま次のリリースで出うる
- **依存のインストールは新しいワークツリーでやり直しになる。** `node_modules` のような追跡外のフォルダは前のワークツリーから引き継がれない。入れ忘れると型チェックやビルドが依存の欠落で落ち、コードの不具合と見分けにくい（ジャンクションで省くなら、下記「ワークツリーを消す前に、ジャンクションを外す」を守る）
- **派生したブランチは、前のブランチのコミットをすべて含む。** 派生側をリリースすれば、前の分も一緒に main へ入る。前のブランチを「まだ直したい」で `worktree/*` へ戻したなら、派生側も `ready/` へ出さない（戻した前の分が、完成していないまま出る）。**派生側が既に `ready/*` なら、前を戻すのと同じときに派生側も `worktree/*` へ戻す。** 前の分を直したら、派生側へ `git merge` で取り込んでから、あらためて改名へ進める

### ワークツリーに入れないとき・入ったまま他を触れないとき

**`EnterWorktree(path: ...)` が拒否されることがある。** ある配布先で 2026-08-22 に次の形で拒否された（別のリポジトリでは 2026-10-20 に `EnterWorktree(path: ...)` が通っている。どの条件で拒否されるかは確かめていない）。

> Refusing to use ... as an isolation worktree: the protected checkout ... has git metadata that could not be resolved

拒否されても止まらない。Step 1 の作成だけ済ませ、以降は**入らずに絶対パスで扱う**。

- git: `git -C <ワークツリーの絶対パス> <サブコマンド>`
- ファイル: Read / Edit / Write に絶対パスを渡す
- ビルド・テスト: 宛先をコマンドの中で指す（`npm --prefix <パス>`・`<パス>/node_modules/.bin/vitest run --root <パス>` など）。`cd <パス> && <コマンド>` は、許可設定に当たらず確認待ちになったり、`&&` の複合コマンドとして止められたりする（[command-execution.md](./command-execution.md)「作業ディレクトリはコマンドの中で固定する」）
- サブエージェント: プロンプトにワークツリーの絶対パスを書く
- 入っていないので `ExitWorktree` も要らない（`git worktree add` で作っただけのワークツリーには作用せず、`No-op: there is no active EnterWorktree session to exit.` を返す）

**入ったセッションからは、他のワークツリーやメインの checkout を対象にした git 操作が拒否されることがある。** `git -C <別のパス>` も `cd <別のパス> && git ...` も拒否された。サブエージェントも同じ制約を受ける（レビューのエージェントが `git diff` を取れず、ファイルを全文読んで代えた例がある）。拒否されなかったのは `git worktree add`・`git worktree list`・ビルドとテスト。同じ配布先では、`&&` で繋いだ複合コマンドや、`sed -n "$(...)"` のように実行時に値が決まるコマンドも拒否された（単純なコマンドに割るか、Grep ツールで代える）。

- **1 セッション 1 ワークツリーを原則にする。** 入ったら、そのワークツリーの作業をコミットまで済ませる。入ったまま別のワークツリーを切って続きを書くと、実装・検証・レビューまで終えてからコミットだけ打てなくなる（実際に起きた）
- **複数のワークツリーを横断する作業**（積んだブランチをまとめて扱う・依存先のリポジトリでビルドする等）は、**入らずに**リポジトリのトップレベルを作業ディレクトリにしたまま、絶対パスで扱う（この形で 6 本のワークツリーを扱い、マージ・リリース・片付けまで終えた例がある）
- それでも入ったセッションからコミットが要るときは、コミットメッセージをファイルへ書き出し、`git -C <ワークツリーの絶対パス> commit -a -F <メッセージのファイル>` をユーザーに実行してもらう。引用符・改行の問題が起きない（`-a` は追跡済みのファイルだけを拾うので、新しいファイルがあれば先に `git add` してもらう）

## 完了時の改名

作業が完了したら、ブランチ名の接頭辞を `ready/` に付け替える。**改名前に必ずユーザーに確認を取る**（下記「なぜ確認が要るか」参照）。

確認は **AskUserQuestion** で次の 4 択を提示する。改名の可否と「この後どこまで進めるか」を一度に決められるため、確認は原則 1 回で済む。

**ラベルは短く保ち、動作の詳細は選択肢の説明文へ回す。** 一覧を一瞥して 1 と 2 の違いが分かることが大事。

| # | ラベル | 動作 |
|---|---|---|
| 1 | リリース待ちのみ | 改名だけ行い、ワークツリーは残す |
| 2 | リリース待ち＋片付け | 改名後、ワークツリーのディレクトリも削除する（**ブランチは残す**。下記「削除手順」参照） |
| 3 | 続けてリリース | 改名後、そのままリリース手続きへ進む |
| 4 | まだ改名しない | `worktree/*` のまま留める（追加で直す予定がある場合）。待ち行列に現れないため、後日あらためてこの手順に戻る |

**提示する順番は、番号とは別に決める**（2026-10-21 ユーザー承認）。番号と動作は上の表のまま変えず、AskUserQuestion に並べる順だけを状況で変える。一番上の選択肢に「(Recommended)」を付ける。

| 状況 | 一番上に置くもの |
|---|---|
| 既定（下の 2 行のどちらにも当たらない） | **2 リリース待ち＋片付け** |
| 会話から「同じワークツリーで手直しを続ける」と読み取れる根拠がある | 1 リリース待ちのみ |
| ユーザーがリリースを指示していた、またはリリースまで進めるのが妥当と判断できる理由がある | 3 続けてリリース |

- **既定を 2 にする理由**: ユーザーは、この後に作業があるか分からないとき一番上を選ぶ。1 を上に置くと、作業がそのまま終わったときにワークツリーが片付けられずに残る。2 なら、後に作業が無くても何も残らない。後に作業があっても困らない —— 同じブランチを手直しするなら、ブランチが残っているのでワークツリーは 1 行で作り直せる（改名後の手直しはどのみち `worktree/*` へ戻す決まり。下記）。別の作業や、リリース待ちのブランチから派生させて積むタスクなら、新しいワークツリーを切るので前のワークツリーは要らない（上記「リリース待ちのブランチから派生させて次を積む」）
- **1 を一番上にするのは、根拠があるときだけ。** 根拠は会話の中で指させるもの（ユーザーが続きの手直しを口にしている等）。「まだ直したいかもしれない」という先読みは根拠にしない
- **3 は、理由が無ければ一番上に置かない。** push は取り消せないので、迷って一番上を選んだだけで出てしまう並びにしない
- **4 は一番上に置かない。** 4 択を出すのは、自分が作業を完了したと判断したときだけ（下記「確認の出し方」）

確認の出し方は状況で決める。

| 状況 | 出し方 |
|---|---|
| 発言がどの選択肢か一意に指している（「リリース待ちに入れて」＝1。ワークツリーの片付けまで求めていれば 2。「リリースして」＝3、改名前の「まだ直したい」＝4） | 4 択の提示を省略してそれを実行する。改名の可否はその発言で確認が取れている |
| 発言から一意に決まらず（「コミットして」等）、**自分（Claude）が作業を完了したと判断できない**（追加のフェーズ・修正が続く見込みがある／完了か継続か判断がつかない） | **4 択を出さない。** コミットと取り込みだけで止め、`ready/` の話は持ち出さない。コミットのたびに聞き直さない |
| 発言から一意に決まらないが、**自分（Claude）が作業を完了したと判断できる** | 4 択を出す。**判断の主体は自分であって、ユーザーが完了を明言したかどうかではない。** ユーザーの意向を先読みして「まだ直したいかもしれないから」と自主的に省略しない——聞くコストは低く、続きがあるならユーザーが選択肢 4 を選べば済む |
| 直前の main 取り込みでコンフリクトを解消した、または**解消したか判然としない** | 発言が選択肢を指していても省略せず、**差分を提示してから**確認する |

- コンフリクト解消の有無は、このセッションで取り込みを実行していなければ対象ブランチの最後のマージコミット（`git log --merges -1 <branch>`）のメッセージで判定する。解消時はその旨を明記する運用のため

承認が得られたら改名する。

```bash
git branch -m worktree/<type>/<name> ready/<type>/<name>
```

- **`worktree/*` = 作業中、`ready/*` = 完成・リリース待ち。** この改名だけが「完了」の印になる
- **理由**: 未マージのブランチには「実装途中で中間コミットしただけのもの」と「完成したもの」が混在し、コミット履歴や更新日時からは区別できない。名前で分けておかないと、リリース時に未完成のブランチを本番へ出しうる
- ワークツリーのディレクトリ名（`.claude/worktrees/<name>`）は変わらない。リネームしてもワークツリーはそのまま使える
- **改名後に追加変更が必要になった場合**は、まず `git branch -m ready/<type>/<name> worktree/<type>/<name>` で作業中へ戻してから直す。検証・敵対的レビューを通し、あらためて `ready/` へ改名する。`ready/*` は「いつリリースされてもよい状態」を意味するため、そのまま触らない
  - 選択肢 2 でワークツリーを消していた場合は、**改名を戻した後に** `git worktree add .claude/worktrees/<name> worktree/<type>/<name>` → `EnterWorktree(path: ".claude/worktrees/<name>")` で作業を再開する。ブランチが残っているため巻き戻せる
- 改名を忘れると、そのブランチは待ち行列（`ready/*`）に現れず永久にリリースされない
- 同名の `ready/<type>/<name>` が既にあると改名は失敗する（過去のリリース中断などで残っている場合）。**勝手に別名を付けず**、状況をユーザーに報告して対象を確認する

### なぜ確認が要るか

コミットの承認は「この変更を記録してよいか」であって「完成したか」ではない。`ready/` への改名は**この内容でリリースしてよい**という宣言であり、他セッションやリリース監視がリリース候補として拾い得る状態にする**外向きの操作**にあたる。両者は意味が違うため、別々に確認する。

- 直前に main を取り込んでコンフリクトを解消した場合は、コミット前確認で見せた内容と実際の中身が変わっている（差分提示が必要になるのはこのため。手当ては上記「確認の出し方」の表）
- 単独セッションで作業している場合も改名は行う。「完了した」という状態が名前に残ることに意味があるため

> リリース手続き全体は `release` スキル（`.claude/skills/release/SKILL.md`）を参照。

## マージ後の自己クリーンアップ（任意）

実装セッションを開いたまま待つ場合、自分のブランチがマージされるのを監視して、自分でワークツリーを片付けてよい。**自分のワークツリーは自分で消すのが最も確実**（他セッションのロックに阻まれないため）。

**これは「完了時の改名」で選択肢 1 を選んだ場合の任意作業。** 選択肢 2 を選んだならワークツリーは既に消えているため、監視は張らない。

**ただし条件が 1 つある。**

> **監視に入る前に必ず `ExitWorktree(action: "keep")` でワークツリーを出ること。**
> 居座ったままだとリリース側が `git worktree remove` に失敗する。**片付けを速くするつもりが、かえって妨げることになる。**

監視を始める前に `git branch --show-current` が既定ブランチを返すことを確認する（ワークツリーを出られているかの機械的な確認）。そのうえで `Monitor` を **`timeout_ms: 1800000`（30 分）** で起動する。

**`Monitor` に「期限なし」の指定は無い。** 30 分で必ず切れて期限切れの通知が来るので、**まだ待つ必要があるなら張り直す**。1800000 を超える値を書いても 30 分へ切り詰められる。期限が来ると監視のコマンドごと止まるので、張り直しても古いループが裏に残ることはない。

> かつてこの節は `Monitor` を `persistent: true` で起動すると書いていたが、**そのパラメータは存在せず、渡した値は黙って捨てられていた**（受け取るのは `command` / `ws` / `description` / `timeout_ms` だけ）。ある配布先のトランスクリプトでは、`persistent: true` 付きの呼び出し 42 回に対して期限切れの通知が 40 回あり、**実際には既定の 5 分ごとに切れては張り直していた**。**存在しないパラメータは失敗として現れない**——効いているかどうかは、渡した値ではなく戻り値（期限の表示）で確かめること。

> 以下は既定ブランチが `main` の前提で書いてある。`master` 等で運用するプロジェクトでは読み替えること（`origin/main` も同様）。

```bash
cd <リポジトリのトップレベル>
fails=0
while true; do
  sleep 120
  # ready/ が消えた場合、理由は 2 つある。取り違えると作業場を消す
  git rev-parse --verify --quiet ready/<type>/<name> >/dev/null || {
    if git rev-parse --verify --quiet worktree/<type>/<name> >/dev/null; then
      echo "REVERTED-TO-WORKTREE: 作業中へ戻されました。何もせず監視を終了します"
    else
      echo "ALREADY-CLEANED: ready/<type>/<name>"
    fi
    exit 0
  }
  if git fetch --quiet 2>/dev/null; then
    fails=0
  else
    fails=$((fails + 1))
    [ "$fails" -ge 5 ] && {
      echo "WATCH-ERROR: git fetch が5回連続で失敗しました。監視を終了します"
      exit 1
    }
    continue
  fi
  git merge-base --is-ancestor ready/<type>/<name> origin/main 2>/dev/null && {
    echo "MERGED-AND-PUSHED: ready/<type>/<name>"
    exit 0
  }
done
```

**ループが黙って回り続ける状態を作らないこと。** 上の 2 つの脱出口がそれを担っている。

- **ブランチが先に消された場合** — リリース側が既に片付けた。`ALREADY-CLEANED` で正常終了する。これが無いと `merge-base` が失敗し続け、仕事が終わったのに監視だけが気づかず回り続ける
- **`git fetch` が恒久的に失敗する場合**（資格情報の失効・ネットワーク断） — 5 回連続で `WATCH-ERROR` を出して終了する。これが無いと永久に無音で回る

> この検知はリリース手順の**マージが `--no-ff` であること**に依存している（ブランチの tip が履歴上の祖先として残るため）。マージ方式を変える場合はこの節も見直すこと。

> **見るのは `main` ではなく `origin/main`。ここを間違えると作業が消える。**
> ローカルの `main` はリリース手順 3（マージ）の時点で更新される。しかしその後の統合後の検証で不具合が見つかれば、`git reset --hard origin/main` でマージごと破棄されうる。`main` を見て発火すると、**破棄される前にブランチとワークツリーを消してしまい、作業内容を指す ref が一つも残らない**。`origin/main` は push 成功後にしか進まないため、これを条件にすれば確定後にのみ発火する。

ポーリング間隔をリリース側の監視（ブランチの出現を待つもの）より緩めているのは、待つ対象が違うため。あちらはブランチの出現、こちらは push の完了を待つ。

**30 分・`sleep 120` なので、1 回の監視で 15 回ポーリングする。** それで決着しなければ期限切れの通知が来る。このループは毎回いまの状態を見るので、張り直しても取りこぼしは無い。

通知の種類ごとに動きが変わる。

| 通知 | 意味 | すること |
|---|---|---|
| `MERGED-AND-PUSHED` | リリースが確定した | 下記の片付けへ進む |
| `REVERTED-TO-WORKTREE` | ユーザーが「まだ直したい」で作業中へ戻した | **何もしない。** 作業を再開する場所なので消してはならない |
| `ALREADY-CLEANED` | リリース側が既に片付けた | 何もしない |
| `WATCH-ERROR` | `git fetch` が繰り返し失敗した | ユーザーに報告する |
| 期限切れ（上のどれも出ずに 30 分経った） | まだリリースされていない | 待ち続けるなら張り直す。やめるなら何もしない |

`MERGED-AND-PUSHED` の場合の片付け:

1. `git worktree list` で**自分のワークツリーがまだ残っているか確認する**
2. **削除してよいかユーザーに確認する。** 他の削除経路（リリース手順・取りこぼし検出）はすべて確認を課している。ここだけ無確認にする理由はない
3. 承認後、下記「削除手順」で片付ける（ワークツリーは「ワークツリーを消す前に、ジャンクションを外す」のコマンドで消す）
4. **既に無ければ何もしない。** リリース側が先に片付けただけであり、エラーではない。確認した直後にリリース側が消すこともあるので、削除コマンドが `ALREADY-GONE` を出しても、`git worktree list` から消えていれば正常として扱う

**これは「うまくいけば早く片付く」という上積みにすぎない。** 監視が働かなくても、次のリリースの取りこぼし検出で必ず回収される。先着順でよく、競合を調停する仕組みは要らない。

## 削除手順

**ブランチの削除（Step 4）はリリース済みのものだけを対象とする。** ワークツリー内にいる場合は先に抜けてから削除する。

```bash
# Step 1: ワークツリーから抜ける（ディレクトリは保持）
ExitWorktree(action: "keep")

# Step 2: ブランチとディレクトリの対応を確認する
git worktree list

# Step 3: ワークツリーディレクトリを削除する
#   下記「ワークツリーを消す前に、ジャンクションを外す」のコマンドを、.claude/worktrees/<name> を指定して実行する
#   （素の git worktree remove は叩かない）

# Step 4: ブランチを削除
git branch -d ready/<type>/<name>
```

- ブランチ名とディレクトリ名は接頭辞が異なるため、**必ず `git worktree list` で対応を確認してから削除する**
- **`--force` / `-D` は使わない。** 他セッションの作業ディレクトリを消す操作であり、取り返しがつかない
- 削除が失敗する典型は次のとおり。**いずれもユーザーに状況を提示して確認する**。まずエラーメッセージを読んで、どれに当たるかを切り分ける
  - 別セッションのシェルがそのディレクトリを作業ディレクトリにしたまま残っている（`cd` で移動 → だめなら PowerShell の `Remove-Item -Recurse -Force`。**ただし下記「ワークツリーを消す前に、ジャンクションを外す」のコマンドでジャンクションが残っていないことを確かめた後に限る** —— 残ったまま掛けると、ジャンクションを辿ってメイン側の中身まで消しうる）。`ExitWorktree` は表示上の作業ディレクトリを戻すだけで、Bash のシェル（バックグラウンドで起こしたものを含む）の作業ディレクトリまでは動かさないことがある。消す前に `pwd`（Bash）・`Get-Location`（PowerShell）で確かめる
  - コード解析ツール（Serena 等）がそのパスをプロジェクトとして掴んだまま（別パスへ再アクティベート）。このツールの掴み方は、プロセスのコマンドラインを探しても見つからない
  - **サーバーの子プロセス・ビルドの補助プロセスが掴んでいる。** dev サーバーのタスクを止めても、ポートを待ち受けている子プロセスは残ることがある（`netstat -ano` で PID を引いて `Stop-Process -Id <PID>`。手順は [verification.md](./verification.md)「dev サーバーの扱い」）。それを止めても `esbuild.exe` のような補助プロセスが別に生きていることがあり、実行ファイルがワークツリーの中にあるので `Get-Process | Where-Object { $_.Path -like "*<ワークツリー名>*" }` で見つかる（PID を指定して止める）。**`.node` のようにライブラリとして読み込まれたファイルは、掴んでいるプロセスの `Path` に出ないので、この方法では見つからない**
  - **別セッションが dev サーバーを立てたまま、リリース側が消した。** git の登録とブランチだけが外れ、ファイルの実体が残る。以後 `git worktree remove` は `is not a working tree` を返す。登録はもう無いので、残ったディレクトリは通常のディレクトリとして消す（ジャンクションの確認は下記のコマンドで済ませてから）。**防ぐには、リリースを他のセッションに任せる前に、実装セッションが自分の dev / preview サーバーを止めておく**
  - **`Permission denied` で失敗しても、ほぼ済んでいることがある。** 自分のシェルの作業ディレクトリがワークツリーの中にあったときなどに、中身と git の登録（`.git/worktrees/<name>`）は外れ、最後の空ディレクトリの削除だけが失敗する。外へ出てやり直すと `is not a working tree` になるが、**これは新しい失敗ではなく、1 回目がほぼ済んでいた印**。`--force` や `Remove-Item -Recurse -Force` へ進まず、`git worktree list` と `git branch --list` で、登録が外れていること・**ブランチ（`ready/*`）が残っていること**を確かめる。`ls -A <ディレクトリ>` が空なら `rmdir` で消す。それも `being used by another process` で消えない（そのセッションで使ったブラウザ操作の MCP がパスを掴んでいる、など）なら、空ディレクトリは残してユーザーへ報告する。MCP サーバーを止めて解こうとしない（他の作業を巻き込む）
  - `contains modified or untracked files` と出る場合はロックではない。サブエージェントが検証用に作った使い捨てファイルが残っていることがある（片付けるよう指示しても残していくことがある）。`git -C <worktree> status --short --untracked-files=all` で中身を確認してから消す。予防には、エージェントのプロンプトで検証用のファイルを作る場所をワークツリーの外に指定する。**git を使う検証なら短いパスを指定する** —— 深いパスでは Windows の 260 文字の制限に当たり、`git push` が `Filename too long` で失敗することがある（長いパスを含むリポジトリを写すときは `git -c core.longpaths=true clone`）

### 孤児のディレクトリをまとめて消すとき

`git worktree list` に載っていないのにディレクトリだけ残っているもの（孤児）を、まとめて片付けることがある。**削除を実行する直前に `git worktree list` を取り直し、そこに載っているものを除外する。** 調べたときに作った削除対象の一覧を、そのまま実行に使わない。

- **調べてから消すまでの間に、他のセッションがワークツリーを作ることがある。** 孤児と判定した 22 個を数分後に消したら対象が 23 個に増えており、その間に別のセッションが作った作業中のワークツリーの中身を消した例がある（ブランチとコミットは無事だったが、未コミットの作業は戻らなかった）
- 除外の一覧は、直前に取った `git worktree list` の出力から作る。名前を書き並べた配列を使い回さない
- **空に近いディレクトリで `git -C <ディレクトリ> status` や `git log` を叩くと、メインのリポジトリの結果が返る**（親を遡って `.git` を見つけるため）。「変更なし」に見えても、それは対象の状態ではない。中身の有無は `ls -A` で直接見る
- ロックで削除が弾かれたディレクトリが出たら、「守られた」ではなく「消しかけた」と考え、中身が残っているかを確かめる
- ブランチも消すなら、直前に `git worktree list --porcelain` でそのブランチを使っているワークツリーが無いことを確かめてから `-d` で消す。**`ready/*` はリリースの待ち行列なので消さない**
- 消す一覧はユーザーへ提示し、承認を得てから消す
- 消し方は 1 つずつ、下記「ワークツリーを消す前に、ジャンクションを外す」のコマンドを通す。孤児は登録が無いので最後の `git worktree remove` が失敗して `WORKTREE-REMOVE-FAILED` が出る（git は `is not a working tree` と返す）。`JUNCTION-STILL-THERE`・`CHECK-FAILED` が出なかったことが、ジャンクションが外れた確認になる
- **`Remove-Item -LiteralPath <ディレクトリ> -Recurse -Force` へ進むのは、次の 3 つが揃ったものだけ。** `WORKTREE-REMOVE-FAILED` が出た・git の返事が `is not a working tree` だった・**その 1 件を消す直前に取り直した** `git worktree list` に載っていない。1 つでも欠けたら消さずに、その 1 件をユーザーへ提示する

### ワークツリーを消す前に、ジャンクションを外す

**Windows では、ワークツリーの中のフォルダ（`node_modules`・ビルド出力・依存のキャッシュなど）をメインの checkout へのジャンクションにしたまま `git worktree remove` を掛けると、git はジャンクションを辿り、メイン側の中身を消す。** 終了コードは 0 で、警告も出ない。

ジャンクションは、Windows のフォルダを別の場所へ向ける仕掛け（シンボリックリンクの一種で、管理者権限なしで張れる）。依存のインストールを省くために張ることがある（張ること自体は禁じない）。ただし git にもエクスプローラーにも普通のフォルダに見えるので、消すときに中まで再帰する。**張ったら、手放す前に外すこと。** 張り方は問わない。見分け方と外し方だけ知っていればよい。

**ワークツリーは、どの経路でも下のコマンドで消す。** 素の `git worktree remove` は叩かず、`ExitWorktree(action: "remove")` でも消さない（後者がジャンクションを外すかは確かめていない。外す保証が無いので使わない）。いまある経路は次のとおり（**消す経路を新しく足したら、ここへも足すこと**）。

- 上記「完了時の改名」の選択肢 2（下記「マージ前にディレクトリだけ削除する場合」）
- 上記「マージ後の自己クリーンアップ」
- 上記「孤児のディレクトリをまとめて消すとき」
- `release` スキルの手順 7、および手順 1 の残骸の回収（取りこぼし・放置されたワークツリー）
- [mr-review.md](./mr-review.md) のレビュー用ワークツリーの後片付け

**Windows では、リポジトリのトップレベルで PowerShell から下のコマンドを実行する**（Windows PowerShell 5.1 で確かめてある。Claude Code なら PowerShell のツールで実行する。Bash からしか呼べない環境なら、自分で呼び出し方を組み立てずにユーザーへ実行を頼む）。ワークツリーの中のジャンクションをすべて外し、**外れたことを確かめてから**消す。**途中で何か 1 つでも失敗したら、消さずに止まる。** Windows 以外では外すものが無いので、`git worktree remove .claude/worktrees/<name>` で消してよい（git はシンボリックリンクをリンクとして消す、という前提。Windows 以外では確かめていない）。

```powershell
$target = '.claude/worktrees/<name>'
try {
  if (-not (Test-Path -LiteralPath $target)) {
    "ALREADY-GONE: $target"
  } else {
    $wt = (Resolve-Path -LiteralPath $target -ErrorAction Stop).Path
    if ((Get-Item -LiteralPath $wt -Force -ErrorAction Stop).Attributes -band [System.IO.FileAttributes]::ReparsePoint) {
      throw "ワークツリーのルート自体がジャンクションになっている: $wt"
    }
    Get-ChildItem -LiteralPath $wt -Recurse -Force -Directory -Attributes ReparsePoint -ErrorAction Stop |
      ForEach-Object { [System.IO.Directory]::Delete($_.FullName, $false) }
    $left = @(Get-ChildItem -LiteralPath $wt -Recurse -Force -Directory -Attributes ReparsePoint -ErrorAction Stop)
    if ($left.Count -gt 0) {
      "JUNCTION-STILL-THERE（ワークツリーは消さない）:"; $left.FullName
    } else {
      git worktree remove $wt
      if ($LASTEXITCODE -eq 0) { "WORKTREE-REMOVED: $wt" } else { "WORKTREE-REMOVE-FAILED（終了コード $LASTEXITCODE）" }
    }
  }
} catch {
  "CHECK-FAILED（ワークツリーは消さない）: $($_.Exception.Message)"
}
```

- **結果は最後に出る 1 行で読む。** 消えたのは `WORKTREE-REMOVED` が出たときだけ。それ以外（何も出ないときを含む）は消えていないとみなす。`ALREADY-GONE` は「そのパスに何も無い」で、他の経路が先に片付けただけなら正常。**ただしパスの書き間違い・トップレベル以外での実行でも出る**ので、`git worktree list` にもそのワークツリーが無いことを確かめてから正常と読む。list に残っていたら、状況をユーザーに提示する
- **見つけ方はフォルダの属性（ReparsePoint）。** ジャンクションも、向け先が消えた宙吊りのものも拾う。`Get-ChildItem -Recurse` は**拾ったジャンクションの中へは降りない**ので、深さの上限を置かなくても向け先（メイン側）までは走らない。git が辿ってしまうのはフォルダのリンクだけなので、ファイルのリンク（`core.symlinks` を有効にしたリポジトリが追跡しているものなど）は `-Directory` で対象から外し、git に任せる
- 外すのは `[System.IO.Directory]::Delete(<絶対パス>, $false)` に限る。ジャンクションそのものだけを消し、向け先には触れない。**ほかの消し方（`rm -r`・`Remove-Item -Recurse` など）を試して代えないこと**。絶対パス（`FullName`）を渡すのは、.NET が PowerShell の現在の場所を見ないため
- **`-ErrorAction Stop` と `try` で、一覧が取れない（読めないフォルダがある等）・外せない・ルート自体がジャンクション、といった失敗をすべて `CHECK-FAILED` へ落とす。** 失敗を見過ごして `git worktree remove` へ進む経路を作らない
- **`JUNCTION-STILL-THERE`・`CHECK-FAILED` が出たら、ワークツリーは消えていない。** 出た内容をユーザーに提示する
- `WORKTREE-REMOVE-FAILED` が出ても `--force` で押し通さない。扱いは呼び出し元の経路の決まりに従う。**別のシェルが掴んでいて消せないときに `Remove-Item -Recurse -Force` へ切り替えるのも、このコマンドでジャンクションが残っていないことを確かめた後に限る**（残ったまま掛けると、ジャンクションを辿ってメイン側の中身まで消しうる）
- 消し終えたら、メイン側の向け先（`node_modules` なら `node_modules/.bin`）が残っていることを確かめる。**無くなっていたら、メイン側が既に削られている**（このコマンドを通さずに消した経路がある）。インストールし直して戻し、ユーザーに報告する
- ワークツリーの中にいるセッションからは実行しない（先に `ExitWorktree(action: "keep")` で抜ける）。`powershell` や `git worktree remove` の実行で許可を求められるのは正常で、許可設定へ足して黙らせない（[hooks.md](./hooks.md)「引数では絞れない」）

**素の `git worktree remove` で消えた分は戻らない。** 上のコマンドは、消す行を表示に置き換えて確かめてある（2026-10-20。入れ子・宙吊りのジャンクションが外れて向け先が残ること、外せないもの・読めないフォルダ・ルート自体がジャンクションのときに `CHECK-FAILED` で止まること、パスが無いときに `ALREADY-GONE` になること）。素の `git worktree remove` で向け先が全部消えることは、使い捨てのリポジトリで確かめてある（2026-10-06）。

### マージ前にディレクトリだけ削除する場合

「完了時の改名」で**選択肢 2** を選んだときは、マージを待たずに上記の Step 1〜3 を行う。**Step 4（ブランチ削除）は実行しない。**

- **ブランチ（`ready/*`）を残すことが必須。** 消すとリリース候補の列挙に現れず、作業内容を指す ref も失われる
- リリース側はワークツリーが無ければ削除を飛ばし、ブランチの削除は通常どおり行う（`release` スキル手順 7）。先に消しても手続きは成立する
